## 보강 조사 질문

1. **R1-02 — S2를 두 전달 경로로 나누면 결과가 어떻게 달라지는가?** 같은 전용 HOME에서 (a) 기존 공유 데몬에 붙은 TUI, (b) 공유 데몬이 없는 Embedded TUI 각각을 준비하고, 별도 프로세스의 `codex queue`로 전달했을 때 수신 thread가 실제 턴을 시작하는지 확인해야 한다. 원본 추적 기준은 `thread/queue/add → QueuedItemService::enqueue → wake_if_loaded`와 `watch_external_messages → dispatch_if_idle`다. (b)는 최소 10초 감지 주기와 실행 준비 시간을 고려한다. 직접 DB 쓰기를 실험 방법으로 삼지 말고 공식 queue 명령만 사용한다. queue가 성공했는지, 수신 턴이 시작했는지, 결과를 회신했는지를 따로 기록해야 한다.
2. **R1-01 — 실제 송수신 endpoint와 framing은 무엇인가?** 0.155.1의 `app_server_control_socket_path`, `cli/main.rs`의 Proxy 분기, `ide_context/ipc.rs`를 기준으로 endpoint 표를 교체해야 한다. 대상 HOME의 app-server-control 소켓과 IDE ipc.sock을 분리하고, 후자를 wakeup 후보에서 제외할 수 있는지 확인한다.
3. **R1-03 — `agents`를 실행하지 않은 초기 상태에서도 같은 경로인가?** TUI의 실행 인자, `CODEX_HOME`, 기존 데몬 유무를 고정한 뒤 `-c`, `--profile`, `--worktree`, 명시적 `--remote`에 따라 `AppServerTarget`이 무엇으로 결정되는지 조사한다. `agents`는 데몬을 시작하므로 읽기 전용 진단 대신 사용하지 않는다. 데몬이 없는 조건과 이미 있는 조건을 별도 실험으로 남겨야 한다.
4. **R1-04 — 레지스트리가 무엇을 저장해야 대상 thread에 정확히 도달하는가?** Embedded 세션에는 “app-server 주소” 대신 대상 HOME/큐 저장소 식별이 필요한지, remote 세션에는 서버 endpoint와 thread ID가 필요한지 구분한다. `session_queue_commands.rs`의 HOME 선택과 `message_processor.rs`의 process-scoped thread store를 기준으로, 두 HOME에 같은 이름의 세션이 있을 때 잘못 배달되지 않는 키를 정의해야 한다. HOME가 다르면 호출 측 환경을 대상 HOME로 선택하거나 명시적 endpoint를 쓰는 절차가 필요한지 전용 프로필에서 확인한다.
5. **R1-05 — S1의 정책 행렬을 정확한 분기로 만들 수 있는가?** `chunk-9mrd94qp.js`의 `k`를 기준으로 explicit accept/hold/refuse, prompting/bypass/unknown, 정상 from-mode/누락/파싱 실패, emit flag 켜짐/꺼짐, selfSent 유무를 구분한다. `chunk-cyg1gqsq.js`의 `TG`는 정규식과 재직렬화 일치 검사로 봉투를 판정하므로 필드 이름만 넣어서는 충분하지 않다. `senderMode`는 송신 시 모드 getter이고 수신 peer origin의 `fromMode`는 content 봉투에서 추출되는 값이라는 연결을 코드로 명시해야 한다. 이 분기에는 CONFIG_DIR가 없으므로 프로필 차이와 권한 모드 차이를 독립 변수로 시험한다.
6. **R1-06 — 자기 주입과 독립 피어 수신이 실제로 같은 분기를 지나는가?** `chunk-z0hsnf69.js`의 `ye/We/Ge/le`에 따라 ancestry와 childToken이 만드는 selfSent 예외를 분리한다. S1의 송신자는 수신자의 Bash 자식이 아닌 독립 테스트 세션이어야 하며, “Another Claude session” 머리말 대신 hold cause·receipt·수신 턴 시작을 판정 근거로 삼아야 한다. 같은 CONFIG_DIR가 전달의 필수조건이라는 14절 결론은 discovery와 ingress를 나눠 재검토한다.
7. **R1-09 — G3가 요구하는 중간 개입과 발신 권한은 무엇인가?** `service.rs`의 idle/Interrupted 분기 및 `thread_queue_processor.rs`의 입력 타입을 기준으로, busy일 때 다음 턴 대기만 허용할지 현재 턴에 개입할지 정한다. 후자는 `turn/steer` 등 별도 공식 경로의 소유권·지원 여부 조사가 필요하다. 수신 모델에게 발신자가 에이전트임을 전달하는 방법, Codex 승인·샌드박스와 Claude prompting/bypass를 대응시킬 근거, hold 승인 UI와 거부 receipt를 어디서 구현할지 확인해야 한다. 일반 user text에 경고를 붙이는 것만으로 네이티브 peer 신뢰 구분과 동등하다고 가정하지 않는다.
8. **R1-08 — Orca의 PTY/구조화 경로를 provider와 독립된 표로 재구성할 수 있는가?** `structured-mailbox-pointer-host.ts → structured host → Claude SDK/Codex adapter`와 PTY 경로를 나란히 추적한다. Claude와 Codex 모두에서 busy·human approval·attachment 없음·accepted/rejected/unknown 결과가 포인터 보존과 재시도에 어떻게 연결되는지 조사한다. 이 방식의 전제는 외부 TUI 제어가 아니라 Orca 소유 세션이므로 C1 적합성을 따로 판정한다.
9. **R1-07 — hook spool의 생산자와 소비자는 누구인가?** `hook-stdin-contract.ts`에서 생성되는 outbound event와 Orca hook 서버의 수집 경로를 대조하고, 실제 mailbox pointer 전달 경로와 분리해 개별 보고서를 고친다. 정오표에만 오류를 남겨 다음 설계자가 잘못된 절을 계속 인용하지 않도록 해야 한다.
10. **R1-10 — 원격 제어를 켜는 것과 기존 thread에 접속하는 것은 어떻게 다른가?** `remote_control_cmd.rs`, daemon lifecycle, `AppServerTarget` 선택을 함께 추적한다. proxy가 가리키는 기존 서버, foreground remote-control 서버, daemon remote-control 서버 각각이 어떤 HOME·thread store를 사용하며 어떤 TUI와 thread를 공유하는지 먼저 확정한다. 기존 Embedded 세션의 자동 이관은 별도 근거 없이는 지원 기능으로 쓰지 않는다.

## 이 리뷰에서 확인 못 한 것

- 실행 중인 다른 Claude/Codex 세션에 메시지를 보내거나 소켓에 쓰지 않았다. 전용 세션 실행, 데몬 시작·중지, `agents` 실행, queue 송신, remote-control 연결, 모델 호출, 테스트 실행도 하지 않았다. **정적 경로 존재는 실측 배달 성공·지연·정확히 한 번 실행의 증거가 아니다.**
- CLI는 `command codex --version`에서 `0.155.1`, `claude --version`에서 `2.1.278`을 확인했고 queue/agents/app-server/remote-control은 `--help`만 조회했다. Codex 최신 main도 초기에 탐색했지만 이 리뷰의 Codex 결론·줄 번호는 모두 위 0.155.1 태그로 다시 확인했다. 배포 바이너리와 공개 태그의 바이트 수준 동일성은 검증하지 않았다.
- 큐 경로는 로컬 SQLite backend가 있어야 한다. 원본은 InMemory store나 state DB가 없는 app-server에는 queue backend를 설치하지 않고, ephemeral/archived/일부 subagent thread를 거부한다(`C/app-server/src/message_processor.rs:300-307`, `C/app-server/src/request_processors/thread_queue_processor.rs:240-298`). 현재 사용자 세션이 어떤 저장소·실행 유형에 속하는지는 조회하지 않았다.
- 외부 큐 변경 watcher의 테스트 `C/ext/queue/tests/queue_service.rs:571-614`는 별도 state runtime이 같은 SQLite에 기록하는 사례를 구성한다. 테스트 파일을 읽었을 뿐 실행하지 않았으며 두 프로세스의 장애·경합·중복 제출까지 검증했다는 뜻이 아니다. 프로필별 커스텀 state 저장소, 동일 thread의 다중 loader, 수신 프로세스 재시작의 결과는 남아 있다.
- `O/src/main/runtime/orchestration/structured-session-pointer-delivery.ts:83-91`의 mid-turn Codex coalescing 주석은 0.147.0/0.150.1/0.153.4 측정이다. Orca가 idle을 기다리는 구현은 확인했지만 이 주석을 0.155.1의 실측 증거로 쓰지 않았다.
- herdr의 PTY text+Enter 전달은 `src/app/api/agents.rs:194-214`, moai의 poll 수신과 새 app-server 생성은 `internal/cli/mcp_server.go:458-480`, `internal/cli/mcp_codex.go:395-412,603-630`에서 대조했다. 실제 OS별 입력 동작은 시험하지 않았다. Buzz/Agora의 채널·저장소 주장 전수 검증은 담당 범위 밖이며 이 리뷰는 그 보고서의 정확성을 승인하지 않는다.
