## 보강 조사 질문

1. **R4-01:** `worker-start --on`에서 `callRuntimeEnvironment`의 one-shot/shared-control 분기를 각각 끝까지 추적했을 때 실제 연결 endpoint, E2EE handshake, device-token 검증은 어디에서 이루어지는가? SSH PTY 경로와 분리한 호출 그래프를 위 Orca 파일들로 작성하면 잘못된 전송·인증 설명을 해소할 수 있다.
2. **R4-02:** pairing revision이나 공개키가 바뀌고 이전 dispatch·relay 항목이 남았을 때 무엇을 재시도하고 무엇을 영구 거부하는가? `federation-sync.ts`, `runtime-environment-revision-guard.ts`, device registry 철회 코드 및 federation 테스트를 근거로 ADR의 신뢰 수명 규약을 채워야 한다.
3. **R4-07:** 같은 thread를 기존 TUI와 새 app-server가 동시에 소유할 수 있는가? Orca adoption 충돌 검사와 실제 설치 Codex의 thread resume/소유권 구현을 먼저 대조하고, 이후 별도 허가된 테스트 세션으로만 확인해야 한다. Orca 주석은 검증할 가설로 남겨야 한다.
4. **R4-08:** `--remote`, `remote-control`, 로컬 shared daemon은 같은 thread 집합과 인증 범위를 공유하는가? 설치 버전에 맞는 Codex 소스/공식 명세에서 연결·pairing·queue 라우팅을 확인하고, 서로 다른 `CODEX_HOME`의 기존 TUI까지 도달하는지 별도 시험 항목으로 분리해야 한다.
5. **R4-09:** Claude bridge에 외부 클라이언트가 사용하도록 보장된 API 계약이 있는가? 공개 공식 명세와 `ce`의 인증 준비·trusted device 경로를 대조하고, “공식 지원”과 “관찰된 내부 프로토콜”을 구분해야 한다. cross-provider 어댑터의 부재와 구현 불가능도 구분해야 한다.
6. **R4-10:** SSH 중계 수신자가 관측하는 peer PID/uid는 누구이며 원래 발신 머신·세션·권한 모드를 어떻게 검증하는가? `chunk-6kcckmy2.js`의 `Pe/Jht`, inbox 수신 코드, `isolatePeerMachines` 검사와 SSH 포워딩 명세를 대조해 회신 주소 변환·중계 신원 규약을 작성해야 한다.
7. **R4-04:** Buzz mesh가 공유해야 하는 Redis 키·session directory와 PostgreSQL 경계는 무엇인가? `mesh_boot.rs`, `registry.rs`, tunnel directory 및 `main.rs`의 Redis fan-out을 추적해 “독립 relay federation”과 “같은 배치 내 다중 인스턴스”를 구분해야 한다.
8. **R4-05:** 공개 UDP 도달성이 없는 두 머신도 현재 mesh 설정으로 연결되는가? `endpoint.rs`의 relay 비활성화, ready record의 endpoint 주소와 membership admission 코드를 근거로 지원 네트워크 조건·피어 키 허용 범위를 명시해야 한다.
9. **R4-06:** 외부 transcript 채택은 원래 프로세스를 재사용하는가, 새 provider child를 띄우는가? `structured-agent-session-create-adoption.ts`에서 실제 attach/launch 및 handoff 구현까지 추적하고, 임의 외부 PID·PTY를 채택하는 공개 진입점이 있는지 별도로 확인해야 한다. 현 증거는 이력 채택과 Orca PTY 복구까지만 뒷받침한다.
10. **R4-03:** 보고서의 “미포함” 판단을 어떤 파일 목록으로 내렸는가? 같은 커밋의 `crates/buzz-relay-mesh/src/` 전체를 다시 조사하고 사용한 파일·줄을 제시해야 한다.

## 이 리뷰에서 확인 못 한 것

- 원격 서버 연결, SSH 접속, relay 기동, 소켓 쓰기, 실제 에이전트 메시지 전송은 수행하지 않았다. 지정된 코디네이터에 대한 작업 heartbeat·완료 보고만 예외로 사용했다.
- Herdr의 `remote-api-bridge` stdio 중계와 엄격 SSH 옵션은 지정 코드에 존재한다. 다만 계정 설정별 연결 성공, Windows named-pipe ACL, Cloud 경로는 검증하지 않았다. 이 범위에서 추가 WRONG 항목을 만들 근거는 얻지 못했다.
- Orca의 모든 transport fallback, device pairing UI, relay 서비스의 운영 배치까지 추적하지 않았다. 확인한 federation 경로를 근거로 SSH 전용·추가 인증 부재 주장을 반박했으며, 모든 원격 경로가 동일하다고 일반화하지 않았다.
- Orca의 임의 외부 live TUI 채택 부재는 코드베이스 전체에 대한 부재 증명을 하지 않았다. 이력 채택과 소유 PTY 복구가 존재한다는 것만 확인했다.
- Codex remote-control은 도움말만 조회했다. daemon 시작·pairing code 생성·세션 연결은 하지 않았으며 bearer-token/벤더 계정 인증의 내부 관계도 확정하지 않았다.
- Claude bridge의 서버 측 권한·기기 신뢰·계정별 활성화 조건, 내부 events API의 공개 지원 계약은 확인하지 않았다.
- Buzz의 실제 클러스터 구성, mesh 피어 admission 전체, NAT 통과 동작은 실행 검증하지 않았다.
- moai-adk·agora의 원격 프로토콜 구현은 이번 발견의 직접 원본 근거로 사용하지 않았다. 기존 보고서의 “확인 못 함”·“코드 미공개”를 긍정 또는 부정으로 바꾸지 않았다.
