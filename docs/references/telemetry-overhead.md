# 텔레메트리 오버헤드 실측

계측이 xsm의 송수신 경로에 얹는 비용을 잰 기록이다. 계측은 켜져 있는 것이 기본값이므로,
"느껴지지 않는다"가 검증 대상이지 희망 사항이 아니다. 사람이 느끼는 계측은 사람이 끄는 계측이다.

측정 도구: `tools/bench_telemetry.py` (stdlib `timeit`만 사용, 외부 의존성 없음)
실행: `python3 tools/bench_telemetry.py [--json] [--iterations N]`

## 무엇을 재는가

세 조각을 따로 잰다. 실패하는 방식이 서로 다르기 때문이다.

| 조각 | 무엇 | 왜 따로 재는가 |
|---|---|---|
| id 생성 | `os.urandom(16)` + `os.urandom(8)` | syscall. 커널과 플랫폼에 달렸다 |
| 직렬화 | span 한 줄의 `json.dumps` | 순수 CPU. attributes가 늘면 여기가 는다 |
| append | `paths.append_jsonl` (open→write→close) | 디스크. 기계마다 유일하게 크게 갈리는 항목 |

그리고 이 셋을 합친 span 하나 전체를, 실제 코드가 쓰는 그대로(`telemetry.span` 컨텍스트 매니저)
잰다. 벤치마크가 재구현을 재면 실제로 배포되는 코드에 대해서는 아무것도 말해주지 않으므로,
프로덕션 함수를 그대로 import해서 호출한다.

한 번의 send는 span을 두 개 남긴다(`xsm.send`와 `xsm.deliver`). 그래서 "send 1회당 비용"은
span 하나의 두 배로 계산한다.

## 목표

| 항목 | 목표 | 근거 |
|---|---|---|
| send 1회당 절대 오버헤드 | **1ms 미만** | 로컬 send가 10~20ms 수준이므로, 1ms면 측정 잡음에 묻힌다 |
| 로컬 send 대비 상대 비율 | **5% 이내** | SSH 경유(300~500ms)에서는 자동으로 0.1% 아래가 되므로, 판정은 항상 로컬 기준으로 한다 |

## 구현 전 이론 추정치

설계 시점에 stdlib 상식으로 세운 예측이다. 실측과 구분해 남긴다.

| 조각 | 예상 |
|---|---|
| id 쌍 | 2~10µs (엔트로피 풀이 캐시되어 있어 빠름) |
| 직렬화 | 2~10µs |
| append_jsonl | 40~300µs (fsync 없음, 로컬 SSD 가정) |
| 합계(2 span) | 약 50~350µs, 목표치의 5~35% |

가장 불확실한 항목은 append로 봤다. span마다 open/write/close를 반복하는 구조라
파일시스템 상태에 따라 변동폭이 크기 때문이다.

## 실측

### 2026-09-22 · 커밋 f317538 · macOS (darwin), Python 3.14.6, APFS/SSD, 10,000회 반복

| 조각 | 실측 | 이론 범위 | 판정 |
|---|---|---|---|
| id 쌍 (16B + 8B) | 2.71 µs | 2~10 µs | 범위 안 |
| `json.dumps` (span 1줄) | 3.66 µs | 2~10 µs | 범위 안 |
| `append_jsonl` | 83.42 µs | 40~300 µs | 범위 안 |
| span 하나 전체 | 87.39 µs | — | 위 셋의 합(89.8µs)과 일치 |
| **send 1회 (span 2개)** | **0.175 ms** | 0.05~0.35 ms | 범위 안 |

목표 대비: 절대 **0.175ms / 1ms = 17.5%**, 로컬 10ms send 대비 **1.75%**. 둘 다 통과.

예상대로 `append_jsonl`이 전체의 95%를 차지한다. id 생성과 직렬화를 아무리 줄여도
의미가 없고, 더 빠르게 만들어야 할 일이 생긴다면 손댈 곳은 파일 쓰기 한 곳뿐이다.

## 임계치를 넘으면

순서대로 시도한다. 새 스위치를 만드는 것은 마지막이다.

1. **배치화**: span 시작과 종료를 `append_jsonl` 한 번으로 묶는다. 실측상 append가 비용의
   거의 전부이므로, 호출 횟수를 절반으로 줄이는 것이 가장 값싼 개선이다.
2. **그래도 넘으면**: `XSM_NO_TELEMETRY=1`을 기본값 off(계측 켜짐)로 둔 채 문서화하고,
   비용에 민감한 환경에서 사람이 직접 끄게 한다.

자동 회로차단(오버헤드가 임계치를 넘으면 스스로 꺼지는 로직)은 두지 않는다. 언제 꺼졌는지
알기 어려워 디버깅이 더 나빠지고, "계측이 느린 것"은 "계측이 동작을 바꾸는 것"보다 훨씬
가벼운 실패이기 때문이다.

## 회귀 가드

`tests/test_telemetry.py`에 느슨한 스모크 테스트를 둔다. 목표치의 10배(span당 10ms)를
넘을 때만 실패한다. 마이크로벤치를 엄격한 임계치로 CI에 넣으면 기계 부하에 따라 flaky해지므로,
정밀한 판정은 이 문서에서 사람이 한다.
