# ADR-0008: 세션 이름, 주소, 네임스페이스

- 상태: Accepted
- 관련 목표: G1, G2, G5
- 작성일: 2026-09-19

## 질문

각 세션에서 `/rename`으로 붙인 이름을 다른 홈(CONFIG_DIR, CODEX_HOME)과 다른 런타임에서도 주소로 쓸 수 있게 하려면, 이름을 어떻게 해석하고 같은 이름의 충돌을 어떻게 처리하는가?

## 맥락

상세 근거는 `docs/references/supplement/T8-discovery-sender-naming.md` 3절에 있다.

- **네이티브로는 홈이나 런타임을 넘어 이름으로 호출할 수 없다.**
  - Claude는 자기 CONFIG_DIR의 살아 있는 세션만 조회한다.
  - Codex는 자기 CODEX_HOME의 저장된 thread만 조회한다(S2c).
- **두 런타임의 충돌 규칙은 반대다.**
  - Claude: 쓸 때 막는다(코드 기본값 기준. 실측에서는 원격 플래그가 꺼져 있어 막지 않았다, 아래 참고). 플래그 `tengu_session_name_uniqueness`(기본 true)로 CONFIG_DIR 안의 살아 있는 세션끼리 고유성을 강제한다. `/rename`한 쪽이 양보하고, 시작 시 충돌이면 이름을 먼저 얻은 쪽이 유지한다. 비교는 `Tr()` 정규화(NFKC, 소문자, 공백→`-`)로 한다.
  - Codex: 읽을 때 막는다. 고유성을 강제하지 않고, 조회 시 같은 라벨이 여럿이면 "Multiple sessions match … use a session UUID" 오류를 낸다. 대소문자까지 정확히 일치해야 하고, 이름이 없으면 첫 메시지 미리보기를 라벨로 쓴다.
- **홈 사이에는 규칙이 없다.** 메시 계층이 다른 홈 세션의 이름을 바꿀 수단도 없다. 따라서 쓸 때 막는 방식은 쓸 수 없다.
- **Claude는 `@`가 들어간 이름을 주소로 인정하지 않는다**(`jEt()` → `qg()`).
- **실측(S7, `docs/spikes/S3-S6-S7-results.md`)**:
  - Claude의 이름 고유성 강제는 원격 플래그에 달려 있고, 이 계정에서는 **꺼져 있다**(`tengu_session_name_uniqueness: False`). 같은 CONFIG_DIR 안에서도 같은 이름이 공존했다. 따라서 "Claude는 쓸 때 막는다"는 전제에 기댈 수 없다.
  - Codex는 thread가 한 페이지(100개)를 넘으면 이름이 유일해도 "Cannot verify a unique session label across server pages"로 이름 전송을 거부한다. 이 머신의 활성 thread는 2,386개다.
  - Codex 이름에는 `@`가 들어갈 수 있다(`xsm@dup` 저장 확인).
  - 이름을 id(소켓)로 확정한 뒤 대상이 `/rename`해도 전송은 정상 도착했다. Claude는 이전 이름을 `formerNames`에 남긴다.
  - B안 규칙을 구현한 시제품 `tools/mesh_resolve.py`가 실제 데이터에서 의도대로 동작했다. 같은 홈 안의 중복 때문에 `이름 [ref]` 문법이 필요하다.
- **이름은 실행 중에 바뀐다.** 이름을 캐시하면 낡는다(ADR-0001 선택지 D의 "포인터만 저장").
- **비교 실측(S9)**: agent-comms 메시의 이름은 bridge마다 무작위(`codex-6N2V`)이고 기록에 CODEX_HOME이 없어, 같은 폴더의 두 Codex 세션 중 어느 쪽이 어느 프로필인지 구분할 수 없었다. 신원 슬롯 `(harness, cwd)`이 겹치면 두 번째 세션은 임시 ID를 받는다. 한정 이름(`name@homeAlias`)을 만들려면 레지스트리가 홈 정보를 보존해야 한다.

## 선택지

### A. 전역 고유성 강제

- 방식: 메시가 모든 홈의 이름을 모아 중복을 막고, 충돌하면 한쪽 이름을 바꾼다
- 장점: 맨 이름 하나로 항상 호출할 수 있다
- 단점: 다른 홈 세션의 이름을 바꿀 네이티브 수단이 없다. 사용자가 정한 이름을 덮어쓴다. Claude의 양보 로직과 경합한다

### B. 한정 이름 + 모호하면 오류

- 방식:
  - 주소는 `이름@홈별칭`이다(예: `reviewer@claude-4`, `reviewer@codex`). 홈 별칭은 설정 폴더 이름에서 파생한다.
  - 맨 이름은 메시 전체에서 유일할 때만 푼다. 여럿이면 후보 목록(한정 이름, ref, 생존 상태)을 보여 주며 오류를 낸다.
  - 비교는 `Tr()` 정규화로 통일한다.
  - 살아 있는 세션을 우선한다. 꺼진 Codex thread는 한정 이름이나 `--include-offline`으로만 대상이 된다.
  - ref는 `sha256(runtime:home:session_id)` 앞 6자리로 고정한다. 전송 시점에 id로 확정하고, 이후에는 id로 보낸다.
  - 범위(ADR-0004) 필터를 이름 해석보다 먼저 적용한다.
- 장점: 사용자 이름을 건드리지 않는다. Claude의 `[ref]`와 Codex의 모호성 오류라는 네이티브 관례와 맞는다. `@`는 Claude 이름과 충돌하지 않는다.
- 단점: 충돌이 있으면 한정 이름을 알아야 한다. Codex 이름에는 `@`가 들어갈 수 있어 해석 규칙이 필요하다(마지막 `@` 뒤가 알려진 별칭일 때만 한정자로 본다).

### C. 우선순위 규칙으로 자동 선택

- 방식: 여러 개가 일치하면 같은 cwd(프로젝트), 같은 런타임, 최근 활동 순으로 하나를 고른다
- 장점: 대부분의 호출이 맨 이름으로 끝난다
- 단점: 조용한 오배송 위험이 있다. 규칙을 모르는 사용자나 에이전트에게 예측하기 어렵다

### D. ref 전용

- 방식: 이름은 표시용으로만 쓰고 호출은 항상 ref나 id로 한다
- 장점: 모호성이 없다
- 단점: 사람과 에이전트가 쓰기 어렵다. INTENT.md의 "자연스러운 호출"과 멀다

## 결정 전에 정할 세부

- 홈 별칭을 폴더 이름에서 자동 파생할지(`claude-4`), 사용자가 붙이게 할지(`claude-4` → `work`)
- 맨 이름이 여럿과 일치할 때 항상 오류를 낼지(B), 같은 프로젝트를 우선할지(B+C 혼합)
- Codex의 기본 라벨(첫 메시지 미리보기)도 이름 후보에 넣을지. 넣으면 의도치 않은 일치가 생길 수 있다

## 결정

**B를 택한다**(사용자의 계획 승인 2026-09-20, xsm v0.1로 구현).

- **주소.** `이름`, `이름@홈`, `이름 [ref]`, `ref:xxxxxx`, `claude:<id>`, `codex:<id>`. `@` 뒤는 알려진 홈 별칭일 때만 한정자로 본다. Codex 이름에는 `@`가 들어갈 수 있다.
- **ref.** `sha256("runtime:realpath(home):session_id")`의 앞 6자다. 메시지 헤더는 발신자를 ref로 싣는다.
- **해석.** 살아 있는 일치가 둘 이상이면 후보를 보이고 거부한다. 멈춘 것만 일치하면 재개 명령을 보인다. 열려 있지만 미등록이면 그 이유를 보인다.
- **이름의 출처.** 이름은 런타임이 정한다(Claude 네이티브 기록, Codex 상태 DB). 사람이 고른 이름이 아니면(`derived`, `auto`) `xsm who`가 ref를 쓰라고 알린다. xsm이 띄운 워커는 워커 이름을 쓴다.
