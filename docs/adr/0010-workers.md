# ADR-0010: 워커를 띄우고 끝내는 일의 경계

- 상태: Accepted
- 관련 목표: C1
- 작성일: 2026-09-21

## 질문

세션이 작업을 맡길 새 세션(워커)을 특정 런타임·모델·추론 수준으로 띄우고, 과제를 주고, 끝나면 종료하는 일을 xsm이 해도 되는가? 한다면 어디까지 하는가?

## 맥락

- ADR-0003과 INTENT.md는 "codex, claude 위에 별도 진입점 런타임을 만들지 않는다"를 지킨다. 계획 C1(2026-09-20)은 이를 "별도 런타임에 의존하지 않을 것"과 "기성 멀티 하네스(Orca 등)와 공존할 것"으로 좁혔다.
- Orca와 herdr는 앱이나 서버가 계속 떠서 에이전트 터미널을 쥐고 워커를 띄우고 관리한다. xsm에는 그런 상주 프로세스가 없다.
- 실측(2026-09-21, `docs/xsm/TESTPLAN.md` 10장):
  - `claude -p --input-format stream-json`은 표준 입력을 워커 자신이 읽기·쓰기로 연 FIFO로 주면 EOF 없이 계속 살고, 수신 소켓과 훅이 TUI와 똑같이 동작한다. 기존 소켓 전달이 그대로 통한다.
  - 헤드리스 Claude에서 `PermissionRequest` 훅은 승인이 필요할 때만 뜨고, 훅이 25초 기다렸다 답해도 받아들이며, 거부 사유가 모델에 전달된다.
  - `codex exec resume`은 큐에 쌓인 메시지를 먼저 처리하지만 프롬프트 없이는 돌지 않는다.
  - 에이전트의 셸 도구에는 TTY가 없다(`/dev/tty` 열기 실패).
- TUI는 터미널을 붙잡고 있을 프로세스가 있어야 산다. tmux가 없는 셸에서 그 역할을 xsm이 하려면 상주 프로세스가 생긴다.

## 선택지

### A. 하지 않는다. 워커 관리는 Orca 같은 도구에 맡긴다

- 장점: 원칙에 가장 가깝다.
- 단점: 그런 도구 밖에서 쓰는 사용자는 워커를 쓸 수 없다.

### B. xsm이 워커를 띄우되, 있는 것에 올라탄다

- 방식: tmux 안이면 부른 패널을 나눠 TUI로, 아니면 헤드리스로 띄운다. Orca·herdr 안에서는 띄우지 않는다.
- 장점: 상주 프로세스 없이 동작한다. 헤드리스 Claude는 FIFO로, 헤드리스 Codex는 턴마다 뜨는 pump로 돈다. 프레임워크와 역할이 겹치지 않는다.
- 단점: 헤드리스 워커의 승인 창에 답할 사람이 없다.

### C. xsm이 자체 PTY 관리자를 둔다

- 장점: 어디서든 TUI 워커를 띄울 수 있다.
- 단점: 상주 프로세스가 생긴다. 사실상 tmux나 Orca를 다시 만드는 셈이다.

## 근거

- 스파이크: 이 ADR 맥락 절의 실측. 기록은 `docs/xsm/TESTPLAN.md` 10장에 있다.
- 레퍼런스: `docs/references/orca.md`. herdr는 `herdr --help`, `HERDR_PANE_ID`·`HERDR_ENV` 환경변수.

## 결정

**B를 택한다**(사용자 결정, 2026-09-21).

- **tmux 안:** 부른 패널 옆에 실제 TUI 워커를 띄운다. 승인은 그 패널에서 사람이 답한다.
- **일반 셸:** ~~헤드리스로 띄운다.~~ **백그라운드 tmux 세션(`xsm-workers`)의 창에 실제 TUI로 띄운다**(2026-09-22 변경, 아래 부록). 승인 요청은 Claude 워커 전용 `PermissionRequest` 훅이 xsm으로 넘기고, 사람이 터미널에서 `xsm approve`/`deny`로 답한다. 대기 한도를 넘기면 거부한다.
- **Orca·herdr 패널 안:** `spawn`과 `stop`을 거부한다. xsm은 메시지 전달만 한다.
- **승인 경로에서 사람을 가리는 검사**(TTY와 에이전트 표식)는 보안 경계가 아니다. 에이전트가 습관처럼 또는 피어의 지시로 승인하는 것을 막는 장치다. 같은 사용자 권한의 에이전트가 작정하고 우회하는 것은 막지 못한다. xsm 검문의 다른 부분과 같은 한계다.

기각한 선택지:

- **A:** 프레임워크 밖의 사용자에게 워커가 아예 없어진다.
- **C:** 상주 프로세스를 들여 C1과 ADR-0003의 취지에 어긋난다.

미해결:

- Codex 워커의 승인 전달: `codex exec`는 승인 정책을 `never`로 강제해 불가능했다. 그래서 헤드리스 Codex 턴을 `codex app-server`로 옮겼다. 턴마다 잠깐 떴다가 끝나므로 상주 프로세스는 아니다. app-server는 승인 요청을 클라이언트에 보내고 답을 기다리므로, xsm이 사람에게 넘길 수 있다(실측, 2026-09-21). 모든 턴에 샌드박스와 승인 정책을 명시해 사용자 설정(YOLO)으로 돌아가지 않게 한다. 패널 Codex도 같은 이유로 `-s workspace-write -a on-request`로 띄운다.
- 워커가 다시 워커를 띄우는 재귀는 `max_depth`(기본 1)로 막는다(사용자 결정, 2026-09-21). 전역값과 spawn 옵션이 있고, 워커는 물려받은 한도를 낮출 수만 있다.
- 동시에 띄우는 워커 수는 `max_workers`(기본 4, 세션마다)로 제한한다. 부모가 끝나거나 사라진 워커는 부모의 SessionEnd, `workers`/`spawn`, 매시간 정리에서 종료한다(2026-09-21 구현·실측).
- **전체 권한(`--full-access`)과 Codex 훅 신뢰 우회(`--trust-hooks`)는 사용자의 명시적 허가가 있을 때만 쓴다**(사용자 결정 2026-09-22). 허가는 MCP `xsm_grant`의 elicitation으로 받고, 1회용이며, 세션·런타임·폴더·옵션에 묶이고, 10분 뒤 만료된다. 사람이 터미널에서 직접 치는 spawn은 허가가 필요 없다. Claude Code auto 모드에서는 분류기가 이 요청 자체를 막을 수 있다(실측). 그 경우 허용은 사용자의 권한 설정으로만 한다.
- **워커가 권한 핑계로 놀아서는 안 된다**(사용자 결정 2026-09-22). 승인 대기는 부모에게 즉시 `task`로 알리고, 부모는 `xsm_approve`(elicitation)로 사용자에게 묻는다. 사용자에게 셸 명령(`!`)을 치게 하지 않는다. 도구 호출이 auto 모드에서 막히면 질문 도구로 먼저 묻는다. 워커는 막힌 단계를 필요한 권한과 함께 보고하고, 부모는 그 권한을 받아 다시 맡긴다.
- 패널 Claude 워커는 `--permission-mode default`로 띄운다. 패널 Codex의 명시적 샌드박스·승인 정책과 같은 규칙이다.

## 부록: 헤드리스 워커를 없앴다 (사용자 결정, 2026-09-22)

워커는 **절대 `claude -p`나 `codex exec`로 띄우지 않는다.** 사용자: "헤드리스는 xsm이 필요 없고
1회성으로 발사하는거지", "절대 claude -p, codex exec가 아니라고." 헤드리스는 일을 던지고 결과를
받는 방식이라 세션 사이의 대화가 없다. xsm은 떠 있는 세션들을 잇는 도구이므로, 헤드리스 워커는
xsm의 대상이 아니다.

- tmux 밖에서 부른 `spawn`, 또는 `--background`는 분리된 tmux 세션 `xsm-workers`에 창을 하나 열고
  그 안에서 실제 TUI를 띄운다. 화면 앞에 사람이 없을 뿐, 메시지는 다른 세션과 같은 경로(Claude
  인박스 소켓, `codex queue`)로 받는다. `xsm attach <워커>`가 그 창으로 데려간다.
- 작업 상황은 statusline에 워커마다 이름과 상태(`bg`, `gone`, 승인 대기 수)로 보인다. 폴더 신뢰
  질문도 승인 대기 수에 들어간다.
- 백그라운드 Claude 워커의 승인은 기존 `PermissionRequest` 중계를 그대로 쓴다. 백그라운드 Codex
  워커는 중계할 훅 이벤트가 없어 `-s workspace-write -a never`로 띄운다. 샌드박스 안에서만 일하고
  묻지 않는다.
- **백그라운드 워커의 폴더 신뢰 확인은 사람에게 온다. 사람이 tmux 화면으로 가지 않는다**(사용자 결정,
  2026-09-22: "`tmux attach -t xsm-workers`로 확인하라 — 절대 이 방식에 만족할 수 없음"). spawn은 등록을
  기다리는 동안 창 화면을 읽고, 신뢰 화면이면 권한 요청과 같은 승인 기록(`tool: folder-trust`)을 만든 뒤
  요청 id와 함께 바로 돌아온다. spawn을 부른 에이전트가 셸 호출에 묶여 있으면 `xsm_approve`를 부를 수
  없기 때문이다. 분리된 `xsm worker-finish`가 사람의 답을 기다려 화면에 그 답을 입력하고, 등록을 마치고,
  미뤄둔 `--task`를 보낸다. 거부되거나 한도 안에 답이 없으면 워커를 정리한다. 키는 실측했다: Claude는
  커서가 "No, exit"에서 시작해 허용이 ↓+Enter, 거부가 Enter이고, Codex는 커서가 "Yes, continue"에서
  시작해 허용이 Enter, 거부가 `2`다.
- 같은 이유로 Codex 워커 이름 붙이기(`/rename <이름>` + Enter)는 신뢰 화면이 없을 때만 입력한다. 전에는
  띄운 지 4초 뒤 무조건 입력해서, 그때 신뢰 화면이 떠 있으면 Enter가 "Yes"를 골라 사람 모르게 폴더를
  신뢰했다(창 모드에도 있던 문제).
- tmux는 `spawn`의 전제 조건이 된다. 없으면 `spawn`이 이유와 함께 거부한다. 메시지 전달 자체는
  tmux가 필요 없다.
- 지운 것: 헤드리스 Claude(FIFO + stream-json), 헤드리스 Codex(`codex app-server` 턴, pump,
  수신함, 자동 답장), 스트림 뷰어 형태의 `attach`, `xsm pump`, `--headless`.

**본문 "측정한 사실"의 한 줄은 오늘 재현되지 않았다.** 16행은 "`claude -p --input-format
stream-json`은 … 수신 소켓과 훅이 TUI와 똑같이 동작한다"고 적었다. 2026-09-22에 Claude Code
2.1.278로 같은 방식으로 띄워 확인했을 때, 프로세스는 여러 턴 살아 있었지만 네이티브 세션 파일도
인박스 소켓도 없었다. 헤드리스 Claude 워커에는 메시지를 넣을 수 없었다는 뜻이다. 버전에 따라 달라진
것인지는 확인하지 못했다.
