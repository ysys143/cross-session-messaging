# ADR-0001: 세션 레지스트리 위치와 형식

- 상태: Accepted
- 관련 목표: G1, G2
- 작성일: 2026-09-19

## 질문

서로 다른 CONFIG_DIR의 Claude·Codex 세션을 하나의 목록으로 발견하려면, 세션 레코드를 어디에 어떤 형식으로 두어야 하는가?

## 맥락

- Claude Code는 `$CLAUDE_CONFIG_DIR/sessions/<pid>.json`에 레코드를 둔다. 이것이 프로필 간 격리의 원인이다(`docs/list-agents-cross-session-messaging.md` 6.1절).
- Claude의 inbox 소켓은 프로필과 무관하게 `/tmp/cc-socks/`에 모인다. 다만 소켓만으로는 이름, cwd, sessionId를 알 수 없다(같은 문서 6.2절).
- Codex에는 `codex agents`(공유 app-server 데몬의 세션 목록)가 있다(`docs/plan/README.md` 2.2절).

- (T8) Codex에는 "실행 중인 세션" 파일 레지스트리가 없다. thread는 `$CODEX_HOME/state_5.sqlite`의 `threads`에 영구 저장되고, 큐 전달에는 CODEX_HOME과 thread id가 필요하다(S2c: 다른 HOME이면 즉시 오류).
- (T8) 세션 훅이 id를 준다. Claude 훅 공통 입력은 `session_id`, `transcript_path`, `cwd`, `permission_mode`이고, Codex `UserPromptSubmit` 입력에도 session id와 `permission_mode`가 있다. Claude 레지스트리 레코드에는 권한 모드가 없다.
- (T8) 이름은 실행 중에 `/rename`으로 바뀐다. 공용 레지스트리에 이름을 복사하면 낡는다.
- 상세: `docs/references/supplement/T8-discovery-sender-naming.md` 1절. 이름·네임스페이스는 ADR-0008에서 다룬다.
- **실측(S3, `docs/spikes/S3-S6-S7-results.md`)**:
  - Claude `SessionStart` 시점에 레코드와 소켓이 이미 있고, 훅 환경에 `CLAUDE_CODE_MESSAGING_SOCKET`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CONFIG_DIR`이 있다. `permission_mode`는 `SessionStart`에 없고 `UserPromptSubmit`에 있으며, 모드를 바꾸면 따라 바뀐다.
  - Codex `SessionStart`는 첫 프롬프트로 thread가 생길 때 실행된다. 입력에 `permission_mode`가 있다. 훅의 `session_id`는 큐의 thread id와 같다. 기본 HOME이면 훅 환경에 `CODEX_HOME`이 없으므로 `transcript_path`(`$CODEX_HOME/sessions/…`)에서 유도한다.
  - 강제 종료 시 `SessionEnd` 훅은 실행되지 않고 레코드·키·소켓이 남는다. 생존 판정(PID + 소켓 연결)으로 정확히 걸러진다. **레지스트리는 종료 훅에 의존하지 말고 조회 시 생존 판정을 해야 한다.**
  - Codex 프로젝트 로컬 훅은 신뢰가 없으면 실행되지 않는다. 사용자 설정 없이 실행하려면 `--dangerously-bypass-hook-trust`가 필요하다. 실제 배포에서는 사용자가 훅을 한 번 신뢰해야 한다(ADR-0003).
- **비교 실측(S9, agent-comms·cc-peer)**: 메모리 전용 레지스트리의 실패 방식을 확인했다.
  - 코디네이터가 kill -9로 죽으면 누구도 포트를 다시 열지 않았고, 새 노드가 별도 메시를 만들어 분할됐다. 정상 종료 때만 인계된다(약 192ms).
  - 메시 전체가 내려가면 room과 기록이 사라지고, 크래시한 노드의 잠금 파일이 남는다.
  - cc-peer 로스터와 전송 키 조회는 `$HOME/.claude/sessions`만 보므로 `~/.claude-3`·`~/.claude-4` 세션은 보이지 않는다. pid를 직접 지정해도 실패한다.
  - agent-comms는 신원을 `(harness, cwd)` 슬롯에 묶는다. 같은 폴더의 두 번째 Codex 세션은 임시 ID를 받고, 이 ID는 재시작하면 바뀐다. 메시 기록에는 CODEX_HOME이 없다.

## 선택지

### A. 공유 디렉터리 레지스트리

- 방식: 훅이 `~/.agent-mesh/sessions/`처럼 CONFIG_DIR 밖의 경로에 레코드를 쓴다
- 장점: 단순함. 에이전트 종류와 무관
- 단점: 훅 등록을 프로필마다 해야 함. 비정상 종료 시 잔여 레코드

### B. 기존 레지스트리 연합

- 방식: 각 CONFIG_DIR의 `sessions/`와 `codex agents`를 모두 읽어 합친다
- 장점: 새 상태를 만들지 않음
- 단점: CONFIG_DIR 목록을 알아야 함. 비공개 형식에 의존

### D. 혼합: Claude는 연합, Codex와 보충 정보는 훅

- 방식:
  - Claude 세션은 알려진 CONFIG_DIR들의 `sessions/`를 읽기 전용으로 합친다(B).
  - Codex 세션은 `SessionStart` 훅이 공용 레지스트리에 `{codex_home, thread_id, cwd, pid, 시작시각, transcript_path}`를 쓴다(A).
  - Claude 세션의 `config_dir`와 `permission_mode`는 훅이 보충한다.
  - 공용 레지스트리는 포인터(홈, id)만 가지고, 이름은 조회할 때 원본에서 읽는다.
- 장점: Claude 쪽에 새 상태를 만들지 않는다. Codex의 부족한 부분만 채운다. 이름이 낡지 않는다.
- 단점: 훅 설치가 필요하다(ADR-0003). Claude 네이티브 레코드 형식에 의존한다.

### C. 기존 런타임 재사용

- 방식: Orca 같은 런타임의 세션·터미널 레지스트리를 쓴다
- 장점: 이미 동작함
- 단점: 해당 런타임 밖에서 띄운 세션은 보이지 않음. C1과 충돌 가능

## 결정

**A′를 택한다**(사용자의 계획 승인 2026-09-20, xsm v0.1로 구현).

- 훅이 `{runtime, home, session_id, pid, lstart, cwd}`를 `~/.xsm/sessions/`에 기록한다. 이름·소켓·스레드 상태는 조회할 때 원본에서 읽는다.
- 홈 목록은 훅 기록의 홈과 `homes.json`의 합집합이다. glob으로 추측하지 않는다.
- 런타임은 훅 입력 필드, 대화 기록 위치, 환경변수 순서로 판별한다. 비기본 CODEX_HOME은 대화 기록 경로에서 얻는다.
- **생존 판정.** Claude는 pid·`lstart`·소켓과 네이티브 기록의 현재 세션 id로 판정한다. id가 다르면 대체된 것으로 보고 `ended`로 둔다. Codex는 pid·`lstart`로 판정한다.
- **훅이 없는 세션.** "미등록"으로 표시하고 보내지 않는다. 예외가 하나 있다. 훅이 신뢰된 Codex 홈에서는 CLI가 열린 스레드를 대신 등록한다. 설치와 신뢰가 곧 동의이기 때문이다. 새 TUI는 시작한 뒤 생긴 스레드만 받는다.
- **종료된 세션.** 아래 초안 그대로 구현했다(`ended`/`stale`, 포인터 7일·기록 30일, 재개 명령 안내).

기각한 것: D(모든 홈을 glob으로 열거하는 파일 레지스트리). 2라운드 반론 2·5·6 때문이다.

남은 미확인: Codex `/new` 뒤 SessionStart 재실행 여부, 데몬 모드 TUI에서 훅의 부모 pid.


### 2라운드 결정 초안 (기록)

- **A′: 대칭 포인터 레지스트리.** Claude와 Codex 모두 훅이 `{runtime, home, session_id, pid, lstart}`만 기록한다. 이름·소켓·thread 상태는 조회 시 원본에서 읽는다.
- 홈 목록은 훅 레코드에 적힌 `home`과 사용자가 명시한 홈 목록 파일의 합집합이다. glob으로 추측하지 않는다.
- 런타임은 경로 문자열이 아니라 훅 입력의 필드로 판별한다.
- 조회 시 생존 판정: Claude는 PID·`lstart`·소켓 연결, Codex는 PID·`lstart`와 thread 상태(not-loaded·Interrupted는 "대기됨"으로 알림).
- 훅 레코드가 없는 세션은 "미등록"으로만 표시하고 전송 대상에서 뺀다.
- `permission_mode`는 첫 `UserPromptSubmit` 전까지 "미상"이다.

종료된 세션(2026-09-21 추가, 실측 기반):
- 포인터는 종료해도 지우지 않는다. `claude --resume`이 같은 세션 id로 돌아오므로(pid만 바뀜, ref·이름 유지) 포인터가 곧 재개 후의 주소다.
- `SessionEnd` 훅으로 정상 종료(`ended`)와 흔적 없는 소멸(`stale`)을 구분한다. Codex는 `SessionEnd`가 없어 항상 `stale`이다.
- 멈춘 세션의 포인터는 7일, 원장과 보류 본문은 30일 보관하고, 세션 시작과 CLI 실행 때 한 시간에 한 번까지 정리한다. 상주 프로세스는 두지 않는다.
- 멈춘 상대에게는 보내지 않고, 재개 명령을 함께 돌려준다.

결정 전 확인(S10 후보, Codex 턴 필요): 비기본 CODEX_HOME의 홈 유도, Codex `/new`·resume 후 `SessionStart` 재실행, 데몬 모드 TUI에서 훅의 부모 PID.
# ADR-0002: 에이전트별 전달·wakeup 방식

- 상태: Accepted
- 관련 목표: G2, G3
- 작성일: 2026-09-19

## 질문

수신 세션이 idle이든 작업 중이든 메시지를 받아 처리하게 하려면, 에이전트 종류별로 어떤 전달 경로를 쓸 것인가?

## 맥락

- Claude: inbox 소켓에 줄 단위 JSON을 쓰면 대화 큐에 들어간다. `priority` 값은 `now`/`next`/`later`다. 턴 도중에 오면 "while you were working" 형태로 전달된다(실측, 같은 문서 9.4절, 12절, 13절).
- Codex: `codex queue --thread --message`는 `$CODEX_HOME/queue_1.sqlite`에 쓰고, 실행 중인 TUI의 watcher(10초)가 로드된 idle thread를 깨운다. 코드 경로를 확인했고 S2에서 실측했다(유휴 TUI 깨우기 성공, 진행 중 턴 개입 불가, Interrupted 상태에서는 대기)(`docs/references/supplement/T1-codex-queue.md`).
- 별도 app-server로 같은 thread를 resume하는 방식은 두 writer 분기 위험 때문에 배제한다(`docs/references/supplement/T3-orca-structured-sessions.md`).
- Claude 수신 판정은 봉투의 `from-mode`(발신자 자기 주장)를 쓴다. 봉투가 없으면 bypass 수신자는 보류한다(`docs/references/README.md` 0.5절).
- 터미널 입력 주입(PTY)은 에이전트와 무관하게 쓸 수 있다. herdr는 프롬프트 전체를 주입하고(`herdr/src/app/api/agents.rs:130-215`), orca는 idle일 때만 "메시지 있음" 포인터 한 줄을 주입한 뒤 본문을 CLI로 가져가게 한다(`orca/src/main/runtime/orchestration/formatter.ts:112-122`). 두 방식 모두 터미널을 소유하는 런타임을 전제한다.

- (S1) Claude는 봉투가 없으면 수락돼도 모델이 답장 주소를 모른다. Claude가 보내는 봉투에는 `from-mode`, `from-name`, `hop-chain`이 붙는다.
- (S2, T8) Codex 큐 메시지에는 발신 표시가 없다. 큐 요청 필드가 `thread_id`, `input`, `client_user_message_id`뿐이다. 대신 `UserPromptSubmit` 훅이 `additionalContext`를 덧붙이거나 `decision: "block"`으로 차단할 수 있다(`codex-rs/hooks/src/schema.rs:428-448`).
- 상세: `docs/references/supplement/T8-discovery-sender-naming.md` 2절.
- **실측(S3·S6, `docs/spikes/S3-S6-S7-results.md`)**:
  - Claude: 피어 메시지에도 `UserPromptSubmit` 훅이 실행되고, `prompt`에 원래 봉투 문자열이 들어온다.
  - **(S4)** Codex↔Claude 왕복이 네이티브 수단만으로 성공했다. 단, 샌드박스가 켜진 Codex(`-s workspace-write`)는 셸로 Claude 소켓에 연결하지 못하고(`EPERM`) `codex queue`도 실패한다(`~/.codex/state_5.sqlite` 쓰기 차단). **발신 도구는 샌드박스 밖에서 실행되는 경로(MCP 도구 또는 신뢰된 훅)로 제공해야 한다.** MCP 서버가 샌드박스 밖에서 도는지는 미확인이다.
  - Codex: 큐 입력에도 `UserPromptSubmit` 훅이 실행된다. `additionalContext`는 대화 기록에 `developer` 역할 메시지로 들어가고, 모델이 "사용자 입력이 아니다"를 인지했다. `decision: "block"`을 내면 TUI에 "Blocked by hook"이 뜨지만, **큐 항목은 이미 소비됐고 대화 기록에도 남지 않는다.** 보류와 사람 검토를 원하면 훅이 차단한 메시지를 직접 저장해야 한다.
- **비교 실측(S9, agent-comms)**:
  - 훅 기반 전달(PostToolUse·Stop·UserPromptSubmit `asyncRewake`)은 완전 유휴 Claude를 깨우지 못했다. 이벤트는 파일에 쌓였다가 사람의 프롬프트로 턴이 열린 뒤에야 전달됐다.
  - 유휴 깨우기에 쓰이는 채널 푸시는 `--dangerously-load-development-channels`가 필요하다(미확인).
  - Codex bridge는 도구 응답에 덧붙이는 방식뿐이어서 유휴 Codex에 45초 동안 아무 변화가 없었고, `codex queue`는 쓰지 않는다.
  - 수신자가 크래시한 동안 보낸 메시지는 발신 측에 "Sent"로 남았지만 재시작 후에도 재생되지 않았다. "쓰기 성공"과 "전달·읽음"을 구분해야 한다.

## 선택지

### A. 네이티브 inbox 우선

- 방식: Claude는 소켓, Codex는 `codex queue`를 쓴다(app-server resume은 15행 이유로 제외)
- 장점: 에이전트의 큐잉·권한 경고를 그대로 활용
- 단점: 에이전트마다 어댑터가 필요하고 비공개 프로토콜 변화에 취약

### B. PTY 주입

- 방식: 터미널 멀티플렉서나 Orca terminal send로 입력을 주입한다
- 장점: 모든 CLI에 적용 가능
- 단점: 사용자 입력과 충돌하고, 메시지가 사람 입력으로 보임(권한 경고 없음)

### D. PTY 포인터 + CLI pull

- 방식: 수신 세션이 idle일 때 "메시지 N건, `mesh check` 실행" 한 줄만 입력하고, 본문은 에이전트가 CLI로 가져간다(orca 방식)
- 장점: 본문이 입력창을 거치지 않고, 어떤 CLI에든 적용된다
- 단점: 터미널에 입력할 수단(멀티플렉서, 런타임)이 필요해 C1과 긴장 관계다. 사용자가 입력 중일 때 섞일 수 있다(이번 조사에서 실제 관찰)

### E. 발신 표시 규약 (A와 함께 쓰는 하위 결정)

- 방식:
  - Claude 수신: 네이티브 봉투를 항상 붙이고, `from-mode`에는 발신 세션의 실제 모드를 적는다. 발신자가 Claude면 `from`에 자기 소켓 주소를 적고, Codex면 비운 채 본문에 회신 방법을 적는다.
  - Codex 수신: 본문 맨 앞에 규약 헤더 `[agent-mesh v1 from="…" ref=… kind=… mode=… id=…]`를 두고, 수신 세션의 `UserPromptSubmit` 훅이 경고 문맥(`additionalContext`)을 붙이고 모드 동등성을 적용한다.
- 장점: 두 런타임에서 "사용자 입력이 아니다"라는 의미를 같은 수준으로 전달한다. Claude 쪽은 네이티브 규칙을 그대로 쓴다.
- 단점: 같은 uid면 위조할 수 있어 인증이 아니다. Codex 훅 차단은 큐에서 이미 꺼낸 뒤의 결정이라 보류나 재전송이 없을 수 있다(S6).

### C. MCP 폴링

- 방식: 각 세션에 MCP 도구 `inbox_check`를 두고 에이전트가 가져간다
- 장점: 공식 확장 지점
- 단점: idle 세션을 깨우지 못함(G3 미충족)

## 결정

**A+E+L을 택한다**(사용자 확인: Codex는 턴 경계 전달로 충분하다, 2026-09-20. xsm v0.1로 구현).

- 전달은 네이티브 경로로 한다. Claude는 inbox 소켓, Codex는 `codex queue`다. 발신 결과는 전달이 아니다. 수신 훅의 기록만 `delivered`다.
- 수신 훅이 막을 때는 본문을 먼저 보관한다. 보관에 실패하면 경고를 붙여 통과시킨다.
- Codex는 진행 중인 턴에 끼어들지 않는다. PTY 주입(D)은 쓰지 않는다.
- **보강(ADR-0010).** xsm이 띄운 헤드리스 Codex 워커는 queue 대신 턴마다 잠깐 띄우는 `codex app-server`로 메시지를 받는다. 사용자가 연 Codex 세션에는 계속 queue를 쓴다. 초안의 "app-server를 쓰지 않는다"는 이미 열린 스레드에 두 번째 writer를 붙이지 않는다는 뜻으로 유지한다.

미실측: 샌드박스 Codex의 MCP 발신.


### 2라운드 결정 초안 (기록)

- **A+E+L.** 전달은 네이티브 경로만 쓴다: Claude는 inbox 소켓, Codex는 `codex queue`. app-server resume은 쓰지 않는다(근거는 Orca 주석이며 Codex 실측은 없다).
- **L(전달 원장)**: 발신 도구는 `queued`로 기록한다. `delivered`는 수신 측 `UserPromptSubmit` 훅의 기록으로만 판정한다. 발신 결과 "Sent"나 종료 코드 0을 전달로 보지 않는다.
- Codex 수신 훅이 `block`할 때는 먼저 held 저장소에 본문을 기록한다. 기록에 실패하면 차단하지 않고 경고 문맥을 붙여 통과시킨다.
- 샌드박스(`workspace-write`) Codex가 MCP 도구로 발신하는 것이 실측되기 전까지, Codex 발신 범위는 "샌드박스 밖 실행 또는 신뢰된 훅 경로"로 한정한다.
- G3: Codex의 중간 개입은 지원하지 않는다. 전달 시점은 현재 턴이 끝난 뒤다. Interrupted 대상에는 전송 시 경고를 돌려준다. PTY 주입(D)은 채택하지 않는다.

결정 전 확인: (1) 샌드박스 Codex의 MCP 발신(S10 후보), (2) `--dangerously-bypass-hook-trust` 없이 사용자가 신뢰를 승인한 상태에서 Codex 훅 동작 재확인. 사용자 확인(2026-09-20): Codex의 턴 경계 전달로 G3를 충족한 것으로 본다.
# ADR-0003: 진입점 래퍼 금지의 경계

- 상태: Accepted

## 질문

'codex, claude 위에 오케스트레이션을 위한 별도 진입점 런타임을 만들지 말 것'이라는 제약 아래, 어떤 구성 요소까지 허용되는가?

## 맥락

- INTENT.md: "작업은 codex, claude로 하되, 자연스럽게 다른 종류의 세션에게 메시지를 주고 받을 수 있기를 바람."
- Orca는 자체 데스크톱 런타임이 에이전트 터미널을 띄우는 구조다(`docs/references/orca.md`).
- Claude의 inbox는 세션 프로세스 자체가 연다. 별도 데몬이 없다.

- **실측(S3, S4, `docs/spikes/`)**:
  - Codex 프로젝트 로컬 훅은 사용자가 한 번 신뢰해야 실행된다. 신뢰하지 않으면 시작 시 "Hooks need review … Hooks can run outside the sandbox after you trust them" 대화상자가 뜨고, 기본 선택은 "Continue without trusting"이다.
  - 샌드박스가 켜진 Codex는 셸로 어떤 발신도 하지 못한다. 따라서 "훅·MCP·CLI만 허용"(선택지 A)을 택하더라도, 발신은 CLI가 아니라 샌드박스 밖 경로(MCP 도구, 신뢰된 훅)여야 한다.
  - Claude는 `--settings`나 설정 파일의 훅으로 붙일 수 있다. 상주 프로세스는 필요 없었다(inbox는 세션 프로세스가 연다).
- **비교 실측(S9)**: agent-comms는 래퍼 없이 MCP 서버와 훅만으로 동작하지만, 코디네이터가 기본값으로 제3자 허브(`wss://mesh.exadev.io/`)에 접속하고 npm 레지스트리 버전 조회도 한다. "런타임 없음"은 외부 서비스 의존 없음까지 포함해야 한다.

## 선택지

### A. 훅·MCP·CLI만 허용

- 방식: 상주 프로세스 없이 세션 훅과 일회성 CLI만 쓴다
- 장점: 제약을 가장 엄격하게 지킴
- 단점: Codex 수신 측에 상주 inbox가 없으면 wakeup 불가 가능성

### B. 옆에서 도는 데몬 허용

- 방식: 세션을 감싸지 않는 백그라운드 서비스(레지스트리·릴레이)를 허용한다
- 장점: 원격·범위·기록을 한곳에서 처리
- 단점: 사실상 런타임이 되어 제약의 취지를 흐릴 수 있음

### C. 세션별 사이드카

- 방식: 세션 훅이 세션 수명에 묶인 작은 프로세스를 띄운다
- 장점: 중앙 데몬 없이 상주 inbox 확보
- 단점: 프로세스 관리와 정리 부담

## 결정

**아래 초안의 네 기준을 결정으로 한다**(사용자 해석 2026-09-20). 여기에 위계를 더한다(사용자 결정 2026-09-21).

- **기성 프레임워크 안에서는 메시징만 한다.** Orca·herdr 패널 안에서 xsm은 그 프레임워크가 다루지 않는 세션 간 메시징만 맡는다. 워커를 띄우고 관리하는 일은 그 프레임워크에 맡긴다. 이 범위는 ADR-0010에 적었다.
- 구현은 이 기준을 지킨다. 핵심 경로는 훅, 파일, 일회성 CLI뿐이다. 보조 프로세스(Codex 워커의 pump와 app-server, 분리된 정리 프로세스)는 일이 끝나면 사라진다. 기본값으로 네트워크 리스너나 외부 서비스를 쓰지 않는다.


### 2라운드 결정 초안 (기록)

사용자 확인(2026-09-20): "금지가 초점이 아니라, 별도의 런타임에 의존하게 만드는 것을 해결하고자 했던 것임. 당연히 기성 멀티 하네스는 그대로 사용 가능해야 하고."

따라서 이 ADR의 질문은 "무엇을 금지하는가"가 아니라 "기능이 무엇에 의존하는가"다. 판정 기준:

1. **의존 없음.** 핵심 경로(발견, 전송, 수신 검문, 기록)는 `claude`·`codex` 세션, 훅, 파일, 일회성 CLI만으로 동작한다. 데몬, 코디네이터, 외부 서비스가 없어도 기능이 줄지 않는다.
2. **보조 구성 요소는 선택 사항이다.** 상주 프로세스나 MCP 서버를 두더라도 없거나 죽었을 때 핵심 경로가 유지되고 상태는 파일에 남는다(S9 E6의 반대 사례).
3. **기성 멀티 하네스와 공존한다.** Orca·herdr 같은 하네스 안에서 띄운 세션도 같은 레지스트리·전송 경로로 참여한다. 그 하네스를 필수로 요구하지도, 배제하지도 않는다. 필요하면 옵트인 어댑터로 연결한다.
4. **기본값은 로컬이다.** 외부 네트워크 접속, 리스너, 원격(SSH)·외부 채널(buzz 등)은 사용자가 명시적으로 켠 경우에만 쓴다(근거는 ADR-0004·0007).

전제 조건: Codex 훅은 사용자가 1회 신뢰해야 한다. MCP 서버가 샌드박스 밖에서 도는지는 미확인이다(ADR-0002).

확인할 것: Orca 안에서 띄운 Claude·Codex 세션이 이 레지스트리와 전송 경로에 그대로 참여하는지(S5-4를 공존 검증으로 확장).
# ADR-0004: 통신 범위(scope) 모델

- 상태: Accepted
- 관련 목표: G5
- 작성일: 2026-09-19

## 질문

무분별한 확장을 막기 위해, 어떤 세션이 어떤 세션을 보고 메시지를 보낼 수 있는지를 어떤 단위로 제한하는가?

## 맥락

- Claude의 현재 범위는 '같은 CONFIG_DIR + 같은 uid'다. 프로젝트 개념은 없다.
- Orca는 Run/워크트리/그룹 주소(`@worktree:<id>`, `@claude` 등)를 쓴다(orchestration 가이드, `docs/references/orca.md` 6절).
- INTENT.md는 이것을 확정 사항이 아니라 토론 대상으로 명시한다.
- Claude Code에는 수신 정책 설정이 이미 있다(`docs/references/README.md` 2.3절).
  - `crossSessionInbound`: `accept`/`hold`/`refuse`. 값이 없으면 권한 모드가 같을 때만 자동 전달한다.
  - 우선순위: 관리 정책 > 플래그 > 사용자 설정. 저장소 설정은 더 엄격하게만 바꿀 수 있다.
  - `isolatePeerMachines`: 다른 머신으로 보낼 때 매번 승인을 받는다.
  - 두 설정은 공식 문서(`code.claude.com/docs/en/settings`)에 있는 공개 기능이다.
  - 모드 동등성에 쓰는 `from-mode`는 발신자가 봉투에 스스로 적는 값이다. 인증되지 않으므로 범위 제어의 보안 근거로 쓸 수 없다.

- 범위 정책을 한 번의 핸드셰이크로 "신뢰 관계"로 굳히고 그 관계가 유효할 때만 메시지를 허용하는 방식은 ADR-0009에서 다룬다(실험 설계 `docs/spikes/S8-handshake-plan.md`).
- **비교 실측(S9)**: cc-peer default front는 `~/.claude/sessions`에 있는 Claude 세션을 그 세션의 동의 없이 메시에 올렸다. 범위 정책은 메시지 시점뿐 아니라 세션 편입 시점에도 적용돼야 한다. 같은 실험에서 cc-peer가 기본값으로 `from-mode=bypass`를 주장해, Claude 세션이 아닌 node 프로세스의 메시지가 bypass 수신 세션에서 곧바로 실행됐다.

## 선택지

### A. 프로젝트 정책 파일

- 방식: 저장소에 `.agent-mesh.toml` 같은 허용 목록을 둔다
- 장점: 저장소와 함께 버전 관리
- 단점: 저장소 밖의 세션(홈 디렉터리 작업 등) 처리가 애매함

### B. 명명된 그룹

- 방식: 세션이 시작할 때 그룹에 가입하고, 같은 그룹 안에서만 통신한다
- 장점: 프로젝트 경계와 독립적
- 단점: 가입 절차가 필요

### D. Claude 네이티브 정책 확장

- 방식: 수신 측 정책은 `crossSessionInbound` 의미(accept/hold/refuse, 모드 동등성, 저장소는 강화만)를 그대로 쓴다. Codex 수신 어댑터에도 같은 규칙을 적용한다. 송신 측 범위(누구에게 보일지)만 새로 정의한다
- 장점: 사용자가 이미 아는 설정 체계와 일관된다. Claude 쪽은 추가 구현이 없다
- 단점: 비공개 기능의 의미에 의존한다. 송신 측 범위는 여전히 별도 설계가 필요하다

### C. 제한 없음 + 수신 측 거부

- 방식: 모두 보이되 수신 측 정책으로 거부한다
- 장점: 단순함
- 단점: 목록이 폭증하고 기본값이 느슨함

## 근거

- 스파이크: `docs/plan/README.md` 5장

## 결정

**기본 프로젝트 + 이름 붙인 프로젝트(B의 변형)를 택한다**(사용자 결정 2026-09-20·21, xsm v0.1로 구현).

- **기본 프로젝트.** 모든 세션은 시작한 디렉터리의 프로젝트에 속한다. git 저장소면 `repo:<이름>`, 아니면 `dir:<폴더>`다. 같은 기본 프로젝트끼리는 설정 없이 통신한다.
- **이름 붙인 프로젝트.** `xsm join <이름>`(`/xsm-join`)으로 폴더(저장소 루트) 단위로 가입한다. 기본 프로젝트에 더하는 가입이다. 두 폴더가 모두 같은 이름에 가입해야 열린다. 탈퇴(`leave`)할 때까지 유지된다. 손으로 쓴 범위(`config.json`의 `scopes`)는 그대로 쓸 수 있고, 같은 이름으로 가입하는 것은 거부한다.
- **검사 지점.** 보내기 전과 받는 훅, 두 곳에서 검사한다. 판정은 현재 구성원 경로로 하고, 이름은 표시용이다.
- **목록.** 기본은 이 폴더와 통신할 수 있는 살아 있는 세션만 보인다. `-a`는 전부 보인다.
- **D(네이티브 정책).** Claude 수신 정책(`crossSessionInbound`)은 그대로 두고, xsm은 보류 여부를 예보만 한다. xsm이 띄운 Claude 워커만 `--settings`로 `accept`를 받는다.

기각: A(저장소 안 정책 파일. 저장소 밖 세션을 다루기 어렵다), C(제한 없음).
# ADR-0005: 채널-스레드 기록 저장소

- 상태: Accepted
- 관련 목표: G6
- 작성일: 2026-09-19

## 질문

즉시 전달(mailbox)과 별개로, 사람과 에이전트가 함께 보는 1:N·N:N 채널-스레드 기록을 어디에 둘 것인가?

## 맥락

- INTENT.md: GitHub issue는 정본만 담고, 일상적인 에이전트 간 비동기 소통·작업 기록·중재는 다른 채널에서 한다.
- buzz는 Nostr 이벤트 로그 기반의 자체 호스팅 워크스페이스다. PostgreSQL·Redis를 쓰고 에이전트 연동을 위한 ACP 하니스가 있다(`docs/references/buzz.md` 1절).
- agora는 기록을 append-only Git DAG로 남긴다. 노드마다 result, insight, hypothesis, verification, report 같은 태그를 달고, SQLite 인덱스와 웹 뷰는 Git에서 도출한다(논문 §3.2, §3.4). 코드는 공개되지 않았다(`docs/references/agora.md`).

- **재개(2026-09-22, 사용자 요청).** 그 사이 바뀐 사실:
  - ADR-0003이 Accepted가 됐다. 핵심 경로는 세션, 훅, 파일, 일회성 CLI만으로 동작해야 한다. 보조 구성 요소는 없어도 핵심이 유지돼야 하고, 기본값은 로컬이다.
  - xsm v0.1이 있다. `~/.xsm`의 레지스트리, 메시지별 원장(`ledger/<id>.json`, 수신 영수증), 범위(기본 프로젝트와 이름 붙인 프로젝트), 워커가 이미 동작한다(`docs/xsm/`).
  - **동시 덧붙이기(실측, 2026-09-22).** 16개 프로세스가 한 파일에 `O_APPEND`로 300줄씩 썼다. 한 레코드를 `write()` 한 번으로 쓰고, 레코드 크기는 100B, 4KB, 60KB로 바꿔 가며 쟀다. 세 경우 모두 4,800줄이 섞이거나 사라지지 않았다(로컬 APFS). 잠금이나 데몬 없이 한 파일에 여럿이 기록할 수 있다.
- **MCP elicitation(실측, 2026-09-22).** 최소 stdio MCP 서버를 사용자 설정을 고치지 않고 붙였다. Codex는 `-c mcp_servers.…`로, Claude는 `--mcp-config`로 붙였다.
  - **두 런타임 모두 elicitation을 지원한다.** 초기화 때 클라이언트가 이를 알린다. Codex는 `elicitation: {form, url}`, Claude는 `elicitation: {}`였다.
  - **사람의 답이 모델을 거치지 않는다.** 도구 호출 중에 서버가 `elicitation/create`를 보내자, 두 TUI 모두 질문과 선택지 양식을 사람에게 보였다. 사람이 고른 값은 서버로 바로 돌아왔다. Codex는 `{"action": "accept", "content": {"choice": "memcached"}}`, Claude는 `{"action": "accept", "content": {"choice": "kafka"}}`였다.
  - **Codex가 띄운 MCP 서버는 샌드박스 밖에서 돈다.** `workspace-write` 샌드박스의 Codex에서도 서버 프로세스에는 `CODEX_SANDBOX`가 없었고, `~/.xsm`에 쓸 수 있었다. 유닉스 소켓 접속은 `EPERM`이 아니라 `ECONNREFUSED`였다. 대상 소켓에 받는 쪽이 없었을 뿐이다. 따라서 ADR-0002가 미실측으로 남긴 "샌드박스 Codex의 발신"도 MCP 도구로 풀릴 수 있다.
  - Codex는 MCP 도구마다 호출 허용을 따로 묻는다. Claude는 auto 모드에서 묻지 않았다.
  - **AskUserQuestion의 흔적.** Claude의 대화 기록에는 AskUserQuestion의 질문과 답 원문이 도구 호출 id와 함께 남는다. 거절한 질문에는 답 항목이 없다.
- **근거 재검토(Round 0, 2026-09-22).**
  - **buzz.** 로컬 실행에 PostgreSQL, Redis, relay가 상주해야 하고, 권장 사양은 RAM 2~4GB다(T5:31-104). 게시자마다 Nostr 키쌍이 필요하며, 키 생성 도구는 없다(T5:117-128). Claude/Codex 연동은 검증되지 않았다(T5:491). T5:445와 buzz.md:380-389는 buzz가 "별도 런타임 없음"을 충족한다고 판정했는데, ADR-0003 기준으로는 틀렸다. 상주 스택이 핵심 경로에 들어오기 때문이다. T5가 가정한 VPS와 원격 relay도 "기본값은 로컬"과 부딪힌다.
  - **agora.** 코드가 공개되지 않았다(agora.md:374). 기록 모델은 참고할 만하다. Git을 유일한 상태로 두고, 노드에 태그(result, insight, hypothesis, verification, report)를 달고, 인덱스와 뷰는 거기서 파생한다(agora.md:42-118). 사람은 웹 UI로 쓸 수 없고, 깨우기 기능이 없다(agora.md:313-336).
  - **파일 규약.** 비교는 T5 표 하나뿐이다(T5:455-467). T5가 이 안에 붙인 "Python 데몬 + 소켓 깨우기"와 CRDT는 ADR-0003과 ADR-0006에 부딪힌다. 동시 쓰기는 위 실측으로 해결된다.
  - **어느 자료도 다루지 않은 것.** 로그에 비밀이 새는 문제, 채널에서 GitHub issue로 올리는 절차(T5:426, 모든 구현에서 미구현).

## 선택지

- 보강 조사 T5(`docs/references/supplement/T5-buzz-channel.md`)와 코디네이터 확인:
  - 기본 compose 구성: `relay`(웹 클라이언트 서빙) + PostgreSQL 17 + Redis 7 + MinIO(S3).
  - 에이전트 연동: `buzz-cli`(REST, NIP-98 서명)와 `buzz-dev-mcp`(MCP).
  - Claude/Codex 연동은 미검증이다.
  - 가벼운 파일 규약과의 비교표는 T5 보고서에 있다.

### A. buzz 자체 호스팅

- 방식: buzz relay를 띄우고 에이전트가 CLI/ACP로 게시한다
- 장점: 사람용 UI, 스레드, 검색 제공
- 단점: PostgreSQL·Redis 등 운영 부담

### B. 외부 메신저

- 방식: Slack/Discord 채널을 쓴다
- 장점: 사람이 이미 익숙한 UI
- 단점: 외부 서비스 의존, 에이전트 기록이 외부로 나감

### C. 파일 규약

- 방식: 저장소 안의 append-only `.md`/`.jsonl`/`.sqlite` 규약을 둔다
- 장점: 가볍고 git으로 추적 가능
- 단점: 사람이 보기 좋은 UI가 없음, 동시 쓰기 규약 필요(ADR-0006)

### D. 파일 기록을 핵심으로, 외부 채널은 선택 어댑터로

- 방식: C를 xsm 위에 구체화한다. 채널은 프로젝트(범위)마다 append-only JSONL 파일이다. 레코드 하나는 `write()` 한 번으로 쓴다. 스레드는 `reply-to`/`root`로 이어지고, agora식 태그(`decision`, `result`, `question`, `hypothesis`)를 단다. 사람과 에이전트는 같은 CLI(`xsm post`, `xsm channel show`)로 쓰고 읽는다. 게시글 안의 `@이름`만 기존 `xsm send`로 그 세션을 깨운다. 즉 기록과 호출은 나뉘고, 멘션으로만 이어진다. buzz나 Slack으로 복제하는 것은 사용자가 켤 때만 붙는 어댑터다
- 장점: 새 런타임이 없고, xsm의 범위와 신원을 그대로 쓴다. 채널이 없어도 메시징은 그대로 동작한다. 태그로 걸러 "결정만" 모은 뷰를 GitHub issue로 올릴 재료로 쓸 수 있다
- 단점: 사람이 보기 좋은 UI는 CLI와 파생 마크다운 수준이다. 저장 위치(저장소 안인지 `~/.xsm`인지)에 따라 공유 범위와 비밀 노출 위험이 달라진다

## 결정

**D′를 택한다**(사용자 결정 2026-09-22).

- **저장.** 원본은 `~/.xsm/channels/<채널>/<YYYY-MM>.jsonl`이다. 한 레코드를 `write()` 한 번으로 덧붙이고, 30일 정리 대상에서 뺀다. 저장소에는 사람이 고른 파생 요약만 커밋한다(`xsm channel export`).
- **채널.** 채널은 범위(ADR-0004)다. 세션의 기본 프로젝트나 가입한 이름 붙인 프로젝트에만 쓰고 읽는다.
- **레코드.** id, 시각, 작성자(사람 또는 세션 ref), 태그, 본문, `reply-to`/`root`로 이뤄진다. 스레드는 `reply-to`로 잇는다.
- **작성자.** CLI가 판정한다. 터미널이고 에이전트 표식이 없으면 사람, 등록된 세션이면 그 세션이다.
- **`decision` 태그.** 사람만 단다. 에이전트가 결정을 기록하려면 xsm MCP 도구로 사람에게 묻는다(elicitation). 사람이 고른 답과 질문 원문이 함께 `decision`으로 기록된다. Claude와 Codex가 같은 방식이다(실측). AskUserQuestion 기록을 인용하는 방식은 쓰지 않는다.
- **MCP 서버.** 세션이 띄우고 세션과 함께 끝나는 stdio 프로세스다(ADR-0003). 설치할 때 각 홈에 등록한다. 결정 외에 게시와 조회 도구도 둔다. 샌드박스 Codex는 CLI로 `~/.xsm`에 쓸 수 없기 때문이다.
- **넣지 않은 것.** 멘션으로 깨우기(호출은 `xsm send`로 따로 한다), GitHub issue 자동 올리기, buzz·Slack 어댑터다. 다시 열 조건: 멘션 호출이나 issue 올리기가 실사용에서 반복될 때, 또는 다른 기계·다른 사람과 원본을 나눠야 할 때(ADR-0007과 함께).

한계: 같은 사용자 권한의 에이전트는 파일을 직접 고쳐 작성자나 결정을 위조할 수 있다. 사람 판정과 elicitation이 막는 것은 습관적인 사칭까지다.

# ADR-0006: 공동 문서 편집 규약

- 상태: Accepted
- 관련 목표: G7
- 작성일: 2026-09-19

## 질문

여러 에이전트가 같은 조사 문서를 함께 쓸 때, 충돌과 사본 증식과 무한 잠금·대기를 어떻게 동시에 피하는가?

## 맥락

- 이번 조사에서는 워커마다 다른 파일 하나만 쓰게 해서 충돌을 피했다(`docs/references/*.md`). 이 방식은 사본이 늘어나는 대가가 있다.
- Claude의 수신 측에는 rate limit, 중복 제거, hop-chain 루프 차단이 있다(`docs/list-agents-cross-session-messaging.md` 9.5절).
- 레퍼런스별 동시성 처리(`docs/references/README.md` 2.6절):
  - agora: append-only, 불변 커밋, 병렬 기여를 모두 보존
  - moai: 수신자별 advisory lock, 원자적 교체, claim 10분 뒤 재전달
  - orca: FIFO 배치와 명시적 ack
  - herdr 경고: 원자적 rename만으로는 lost update를 막지 못한다

- **재개(2026-09-22, 사용자 요청).** 그 사이 바뀐 사실:
  - ADR-0005가 Accepted가 됐다. xsm에 범위별 append-only 채널(`~/.xsm/channels/`)이 있고, 사람이 고른 파생 요약을 저장소에 내보낸다(`xsm channel export`). 이것이 선택지 C의 "로그 + 도출 정본"을 이미 절반 구현한다.
  - xsm에 워커가 있다(ADR-0010). 부모 세션이 과제를 나누고, 답을 받아 모으는 통합자 역할을 이미 한다.
  - **선착순 임대(실측, 2026-09-22).** 8개 프로세스가 같은 대상에 대한 임대 레코드를 한 로그에 동시에 덧붙이고, 되읽어 "가장 앞선 살아 있는 임대"를 승자로 판정했다. 50회 모두 승자가 정확히 하나였다. 판정 기준을 기록 시각이 아니라 **파일 안의 줄 순서**로 하면 이론상 경합도 없다. `O_APPEND`는 순서가 하나로 정해지고, 자기 줄을 쓴 뒤 되읽으면 그보다 앞선 줄은 모두 보이기 때문이다. 잠금 파일, 데몬, 시계 동기화가 필요 없다.
  - 동시 덧붙이기는 16개 프로세스, 60KB 레코드에서도 섞이지 않았다(ADR-0005 실측).

## 선택지

### A. 소유권 분할 + 단일 통합자

- 방식: 절(section)마다 소유자를 두고, 통합은 한 세션이 한다
- 장점: 잠금이 필요 없음
- 단점: 통합자가 병목

### B. 기한 있는 임대(lease) 잠금

- 방식: 파일·절 단위로 만료 시간이 있는 잠금을 둔다
- 장점: 무한 대기 방지
- 단점: 만료 처리와 시계 문제

### C. append-only 로그 + 주기적 정리

- 방식: 변경을 로그에 추가하고 정본은 주기적으로 재생성한다
- 장점: 충돌이 없음
- 단점: 정본 재생성 규칙이 필요

### D. Git 브랜치 + PR 병합

- 방식: 에이전트마다 브랜치에서 쓰고, PR과 3-way merge로 합친다
- 장점: 기존 도구와 리뷰 흐름을 그대로 쓴다
- 단점: 충돌 해결 주체가 필요하다. 작은 기록마다 PR을 만들면 비용이 크다

### E. CRDT/OT

- 방식: Automerge·Yjs 같은 CRDT로 동시 편집한다
- 장점: 충돌과 잠금이 없다
- 단점: 동기화 서버나 상주 프로세스가 필요해 C1과 긴장한다. 마크다운 diff 가독성이 떨어진다

### F. 절 단위 소유권 + 명시적 병합

- 방식: 절마다 소유 에이전트를 정하고, 절 사이 변경은 소유자가 병합한다
- 장점: 잠금 없이 충돌을 줄인다
- 단점: 소유권 이전 규칙이 필요하다

보강 조사 T6의 권고: C(append-only + 도출 정본)가 1순위이고, A+C 혼합이 대안이다(`docs/references/supplement/T6-shared-document-editing.md` 3절).

### G. 소유 분할 + 채널 임대 + 통합자 (A·B·C 조합, 제안)

- 방식: 문서를 파일이나 절 단위로 나눈다. 쓰기 전에 채널에 `claim` 레코드(대상, 만료)를 남기고, 로그의 줄 순서로 선착순 판정한다. 진 쪽은 다른 대상을 고르거나 기다린다. 만료가 있으므로 무한 대기가 없다. 끝나면 `release` 또는 `result` 레코드를 남긴다. 정본은 통합자(부모 세션이나 사람)가 소유자별 파일과 채널 기록을 합쳐 만든다. 사본은 "소유자 파일 1개 + 정본 1개"로 한정된다
- 장점: 잠금 파일과 데몬이 없다. 누가 무엇을 쓰는지가 채널에 남아 사람도 본다. 워커 구조와 그대로 맞는다
- 단점: 임대는 규약이다. 규약을 무시하고 쓰는 세션은 막지 못한다. 절 단위 대상의 이름 규칙이 필요하다

## 결정

**agora 방식을 택한다**(사용자 결정 2026-09-22). 선택지 C(append-only 로그와 도출 정본)를 agora의 기록 모델로 구체화한다(`docs/references/agora.md`).

- **노드.** 기여 하나가 바꿀 수 없는 노드 파일 하나다. 위치는 `<문서>.nodes/<id>.md`이고 저장소에 커밋된다. 머리에는 id, 시각, 작성자(xsm이 판정한 사람 또는 세션 ref), 태그, 부모 id 목록을 적는다. id는 내용과 머리의 해시에서 나온다. 이미 있는 노드는 고치지 않는다. 고치려면 부모를 가리키는 새 노드를 쓴다. 노드마다 파일 이름이 다르므로 git 병합에서 충돌하지 않는다. 동시 기여는 모두 보존된다.
- **태그.** agora의 예약 태그를 쓴다. `setup`, `result`, `insight`, `hypothesis`, `verification`, `report`, `wip`, `endorsed`다. `endorsed`는 사람만 단다. 채널의 `decision`과 같은 규칙으로, 터미널의 사람이나 MCP elicitation을 거친다.
- **정본.** `<문서>.md`는 노드에서 만든다(`xsm doc render`). 머리에 "생성된 파일"이라고 적고 손으로 고치지 않는다. 기본 뷰는 가장 최근의 `endorsed`, 없으면 가장 최근의 `report` 노드 본문이다. 그 아래에 아직 이어지지 않은 끝 노드(leaves)와 검증되지 않은 가설 목록을 붙인다. 정본이 병합에서 충돌하면 다시 생성한다.
- **보기.** `xsm doc log|leaves|show`가 있다. agora의 분석 뷰에 해당한다.
- **범위 밖.** 잠금, 임대, 통합자 병목이 없다. 사본은 "노드 + 생성된 정본 1개"다. 노드는 이력이라 늘어나는 것이 설계다. 로컬 파일 시스템과 git만 대상이다.

# ADR-0007: 원격 통신과 신뢰 모델

- 상태: Accepted
- 관련 목표: G4
- 작성일: 2026-09-19

## 질문

SSH로 연결된 다른 머신의 세션과 통신할 때, 어떤 전송 경로와 인증을 쓸 것인가?

## 맥락

- Claude의 로컬 inbox는 같은 uid를 신뢰 경계로 삼는다. 원격에는 그대로 확장할 수 없다.
- Claude의 원격 경로(bridge)는 Anthropic API의 `/v1/sessions/{id}/events`를 경유하고 OAuth 인증을 쓴다(같은 문서 11절).
- Codex는 `--remote ws://|wss://|unix://`와 `--remote-auth-token-env`를 지원한다(`docs/plan/README.md` 2.2절).
- Orca federation은 SSH가 아니다. 페어링된 WebSocket 위에서 공개키 유도 공유키와 기기 토큰을 쓰고, dispatch에 공개키 지문과 pairing revision을 고정해 불일치를 `peer_changed`로 거부한다(`docs/references/supplement/T4-remote-transport.md` 1절).
- Codex `--remote`는 TUI를 원격 app-server에 붙이는 옵션이다. 기존 세션을 원격에서 깨우는 경로는 아니다(T4 3절).
- SSH 포워딩(선택지 A)은 Claude 수신 측의 PID·uid 검증과 `from=uds:` 회신 주소를 그대로 보존하지 못할 수 있다. S5로 확인한다(T4 5절).

- **실측(S5 루프백, `docs/spikes/S4-S5-results.md`)**:
  - SSH 소켓 포워딩(`ssh -L`)을 거치면 수신 측이 보는 peer가 `sshd-session` 프로세스로 바뀐다. 원래 발신자의 PID와 신원은 사라진다.
  - Claude inbox는 포워딩된 메시지를 수락했지만, **로컬 uds 피어로 취급해 `isolatePeerMachines` 원격 승인이 적용되지 않는다.**
  - `ssh 호스트 "codex queue …"`(원격 실행)로 원격 Codex 세션을 깨웠고, 수신 훅의 발신 표시도 동작했다. 소켓 포워딩 없이 SSH 키 인증만으로 된다.
  - **실제 원격(jaesol-macmini)**: 봉투 `from`에 원격 머신의 `uds:` 경로를 그대로 적으면, 답장이 **받는 머신의 같은 경로에 있는 다른 프로세스로 오류 없이 오배송**된다. 수신 머신 기준으로 매핑한 경로를 적으면 정확히 도착한다(반대 방향도 매핑 필요). `isolatePeerMachines: true`인 세션도 `uds:` 경로의 원격 답장을 승인 없이 보냈다.
  - Orca 재페어링과 NAT는 아직 확인하지 않았다.
- **비교 실측(S9 E5, agent-comms)**: tailnet 주소에 연 listener로 `mesh_connect` → `mesh_accept` → DM 왕복이 동작했다. 그러나 연결 요청의 `fingerprint`가 비어 있어 승인자가 대조할 값이 없었고, 승인 action은 에이전트 도구에도 있다. 또 코디네이터는 설정 없이 제3자 허브 `wss://mesh.exadev.io/`에 접속하고, 열어 둔 listener 주소를 허브를 통해 광고한다.

- **재개(2026-09-22, 사용자 요청).** 그 사이 바뀐 사실:
  - xsm v0.1이 있다. 로컬 발견, 전송, 수신 검문, 원장, 범위(기본 프로젝트와 양쪽 가입이 필요한 이름 붙인 프로젝트), 채널이 파일과 일회성 CLI로 동작한다.
  - 원격 실행(D)은 S5-6에서 실측으로 동작했다. `ssh 호스트 "codex queue …"`로 원격 Codex를 깨웠고, 수신 훅의 발신 표시도 동작했다. 소켓 포워딩(A)은 발신자 신원을 `sshd-session`으로 바꾸고, `from=uds:` 경로를 오배송하며, `isolatePeerMachines`를 무력화했다(S5).
  - 허가와 결정을 사람에게 묻는 MCP elicitation이 두 런타임에서 동작한다(ADR-0005 실측). 원격에서 온 첫 연결이나 범위 확장을 받는 쪽 사람에게 물을 수단이 생겼다.

## 선택지

### A. SSH 소켓 포워딩

- 방식: `ssh -L`/`-R`로 원격 유닉스 소켓을 로컬에 연결한다
- 장점: SSH 인증을 그대로 사용, 새 서버 없음
- 단점: 연결 관리를 수동으로 해야 함

### D. SSH 원격 실행 (원격 머신에서 로컬 전달)

- 방식: `ssh 호스트 '<원격의 발신 도구> …'`로 원격 머신에서 로컬 전달(Claude inbox 쓰기, `codex queue`)을 실행한다. 소켓을 포워딩하지 않는다
- 장점: 새 서버가 없다. SSH 인증을 그대로 쓴다. Codex는 S5-6에서 실측으로 동작했다. 원격 머신 안에서는 로컬 규칙(생존 판정, 발신 표시 훅)이 그대로 적용된다
- 단점: 원격 머신에도 발신 도구와 레지스트리가 있어야 한다. 원격임을 알리는 표시는 규약으로 붙여야 한다(`from-name="이름@호스트"` 등). 회신은 반대 방향 SSH가 필요하다
- 실측과의 관계: 소켓 포워딩(A)에서 확인된 오배송과 격리 무력화를 피할 수 있다. 원격 메시지의 `from`을 비우고 회신 방법을 본문 규약으로 적기 때문이다. macOS에서는 원격 머신의 Claude 인증이 로그인 키체인에 묶여 비대화식 SSH에서 새 세션을 띄울 수 없다(수신 대상은 이미 실행 중인 세션이어야 한다)

### B. 인증된 WebSocket 릴레이

- 방식: 토큰 인증 ws 릴레이가 머신 간 메시지를 중계한다
- 장점: 여러 머신으로 확장이 쉬움
- 단점: 상주 서버가 필요(ADR-0003과 연동)

### C. 에이전트 벤더 원격 경로

- 방식: Claude bridge, Codex remote를 에이전트별로 쓴다
- 장점: 공식 경로
- 단점: Claude↔Codex 교차 통신은 불가

### E. xsm 원격 실행 (D를 xsm 위에, 제안)

- 방식: 사용자가 `~/.xsm/config.json`의 `remotes`에 호스트를 선언한다(SSH 별칭). `xsm send 이름@홈@호스트`는 `ssh 호스트 xsm send …`로 원격 머신의 xsm이 로컬 전달하게 한다. 원격 메시지의 봉투에는 `uds:` 회신 주소를 넣지 않는다. 대신 헤더에 `origin=호스트`를 넣고 회신 명령에 호스트를 붙인다. 범위는 양쪽 머신 모두에서 같은 이름의 프로젝트에 가입해야 열린다. 원격에서 처음 들어오는 연결은 받는 쪽 사람에게 elicitation으로 한 번 묻는다. 호스트 신원은 SSH `known_hosts`가 맡는다. `xsm list`는 선언된 원격을 `ssh 호스트 xsm list --json`으로 조회해 합친다
- 장점: 새 서버가 없다. SSH 인증과 호스트 키 고정을 그대로 쓴다. 원격 머신 안에서는 로컬 규칙(생존, 검문, 원장)이 그대로 적용된다. 실측된 오배송과 격리 무력화를 피한다
- 단점: 원격 머신에도 xsm이 설치돼 있어야 한다. 조회와 전송마다 SSH 연결 비용이 든다. 비대화식 SSH에서는 macOS Claude 로그인 키체인 때문에 원격에 새 세션을 띄울 수 없다. 원격 워커는 범위 밖이다

## 결정 전에 사용자가 정할 것

1. 연결 방향: 보내는 쪽에서 나가는 SSH 한 방향만 전제하는가(outbox 회신), 양방향을 요구하는가.
2. 원격 신뢰 단위: 호스트와 키로 충분한가, 세션 단위 신원이 필요한가.
3. 원격 범위: 명시적으로 짝짓는가, 같은 이름이면 여는가.
4. 첫 연결 동의: 선언할 때 사람에게 받는가, 받는 쪽 사람에게 묻는가. 받는 쪽에 사람이 없을 때 hold인가 refuse인가.
5. 목록 병합과 채널 공유를 이번 범위에 넣는가.

## 결정

**E′를 양방향 SSH로 택한다**(사용자 결정 2026-09-22).

- **전제.** 두 기계가 서로 SSH로 들어갈 수 있다. 보내기와 답장 모두 받는 쪽 기계로 가는 SSH 원격 실행이다. 한쪽 방향이 막힌 배치(NAT 뒤 노트북 등)는 지원하지 않는다. 이 경우 연결을 선언할 때 확인해 알린다.
- **수신기.** 받는 쪽 `authorized_keys`의 해당 키에 강제 명령 `xsm recv-remote`를 건다. 원격 메시지는 표준 입력으로 받는다. `origin`(호스트와 키 지문)은 받는 쪽이 SSH 연결 정보로 채우고, 헤더의 주장은 믿지 않는다. 신뢰 단위는 세션이 아니라 호스트와 키다.
- **범위.** `xsm remote add <호스트>`로 로컬 프로젝트와 원격 프로젝트를 명시적으로 짝짓는다. 이름이 같다고 열지 않는다. 받는 쪽도 같은 짝을 선언해야 연다. 받는 쪽 게이트는 선언된 원격이고 짝지은 프로젝트인지를 본다.
- **동의.** 선언할 때 사람에게 받는다. 터미널의 사람이거나, MCP `xsm_grant`와 같은 elicitation이다. 받는 쪽의 기본값은 hold다. 선언되지 않은 원격에서 온 메시지는 보관하고 보낸 쪽에 "보류"를 돌려준다.
- **주소와 답장.** `이름@홈@호스트` 또는 `ref:xxxxxx@호스트`로 보낸다. 봉투에는 `uds:` 회신 주소를 넣지 않는다(S5의 오배송 방지). 답장 명령은 원격 형식으로 붙는다.
- **넣지 않은 것.** 목록 병합, 채널·문서 공유, 원격 워커다. 원격 대상은 살아 있는 세션뿐이다. macOS 키체인 때문에 비대화식 SSH로 새 세션을 띄울 수 없다.
- ADR-0009에서 넘어온 원격 발신자 신원 규칙은 위의 수신기와 범위 규칙으로 정한다.

# ADR-0008: 세션 이름, 주소, 네임스페이스

- 상태: Accepted
- 관련 목표: G1, G2, G5
- 작성일: 2026-09-19

## 질문

각 세션에서 `/rename`으로 붙인 이름을 다른 홈(CONFIG_DIR, CODEX_HOME)과 다른 런타임에서도 주소로 쓸 수 있게 하려면, 이름을 어떻게 해석하고 같은 이름의 충돌을 어떻게 처리하는가?

## 맥락

상세 근거는 `docs/references/supplement/T8-discovery-sender-naming.md` 3절에 있다.

- **네이티브로는 홈이나 런타임을 넘어 이름으로 호출할 수 없다.**
  - Claude는 자기 CONFIG_DIR의 살아 있는 세션만 조회한다.
  - Codex는 자기 CODEX_HOME의 저장된 thread만 조회한다(S2c).
- **두 런타임의 충돌 규칙은 반대다.**
  - Claude: 쓸 때 막는다(코드 기본값 기준. 실측에서는 원격 플래그가 꺼져 있어 막지 않았다, 아래 참고). 플래그 `tengu_session_name_uniqueness`(기본 true)로 CONFIG_DIR 안의 살아 있는 세션끼리 고유성을 강제한다. `/rename`한 쪽이 양보하고, 시작 시 충돌이면 이름을 먼저 얻은 쪽이 유지한다. 비교는 `Tr()` 정규화(NFKC, 소문자, 공백→`-`)로 한다.
  - Codex: 읽을 때 막는다. 고유성을 강제하지 않고, 조회 시 같은 라벨이 여럿이면 "Multiple sessions match … use a session UUID" 오류를 낸다. 대소문자까지 정확히 일치해야 하고, 이름이 없으면 첫 메시지 미리보기를 라벨로 쓴다.
- **홈 사이에는 규칙이 없다.** 메시 계층이 다른 홈 세션의 이름을 바꿀 수단도 없다. 따라서 쓸 때 막는 방식은 쓸 수 없다.
- **Claude는 `@`가 들어간 이름을 주소로 인정하지 않는다**(`jEt()` → `qg()`).
- **실측(S7, `docs/spikes/S3-S6-S7-results.md`)**:
  - Claude의 이름 고유성 강제는 원격 플래그에 달려 있고, 이 계정에서는 **꺼져 있다**(`tengu_session_name_uniqueness: False`). 같은 CONFIG_DIR 안에서도 같은 이름이 공존했다. 따라서 "Claude는 쓸 때 막는다"는 전제에 기댈 수 없다.
  - Codex는 thread가 한 페이지(100개)를 넘으면 이름이 유일해도 "Cannot verify a unique session label across server pages"로 이름 전송을 거부한다. 이 머신의 활성 thread는 2,386개다.
  - Codex 이름에는 `@`가 들어갈 수 있다(`xsm@dup` 저장 확인).
  - 이름을 id(소켓)로 확정한 뒤 대상이 `/rename`해도 전송은 정상 도착했다. Claude는 이전 이름을 `formerNames`에 남긴다.
  - B안 규칙을 구현한 시제품 `tools/mesh_resolve.py`가 실제 데이터에서 의도대로 동작했다. 같은 홈 안의 중복 때문에 `이름 [ref]` 문법이 필요하다.
- **이름은 실행 중에 바뀐다.** 이름을 캐시하면 낡는다(ADR-0001 선택지 D의 "포인터만 저장").
- **비교 실측(S9)**: agent-comms 메시의 이름은 bridge마다 무작위(`codex-6N2V`)이고 기록에 CODEX_HOME이 없어, 같은 폴더의 두 Codex 세션 중 어느 쪽이 어느 프로필인지 구분할 수 없었다. 신원 슬롯 `(harness, cwd)`이 겹치면 두 번째 세션은 임시 ID를 받는다. 한정 이름(`name@homeAlias`)을 만들려면 레지스트리가 홈 정보를 보존해야 한다.

## 선택지

### A. 전역 고유성 강제

- 방식: 메시가 모든 홈의 이름을 모아 중복을 막고, 충돌하면 한쪽 이름을 바꾼다
- 장점: 맨 이름 하나로 항상 호출할 수 있다
- 단점: 다른 홈 세션의 이름을 바꿀 네이티브 수단이 없다. 사용자가 정한 이름을 덮어쓴다. Claude의 양보 로직과 경합한다

### B. 한정 이름 + 모호하면 오류

- 방식:
  - 주소는 `이름@홈별칭`이다(예: `reviewer@claude-4`, `reviewer@codex`). 홈 별칭은 설정 폴더 이름에서 파생한다.
  - 맨 이름은 메시 전체에서 유일할 때만 푼다. 여럿이면 후보 목록(한정 이름, ref, 생존 상태)을 보여 주며 오류를 낸다.
  - 비교는 `Tr()` 정규화로 통일한다.
  - 살아 있는 세션을 우선한다. 꺼진 Codex thread는 한정 이름이나 `--include-offline`으로만 대상이 된다.
  - ref는 `sha256(runtime:home:session_id)` 앞 6자리로 고정한다. 전송 시점에 id로 확정하고, 이후에는 id로 보낸다.
  - 범위(ADR-0004) 필터를 이름 해석보다 먼저 적용한다.
- 장점: 사용자 이름을 건드리지 않는다. Claude의 `[ref]`와 Codex의 모호성 오류라는 네이티브 관례와 맞는다. `@`는 Claude 이름과 충돌하지 않는다.
- 단점: 충돌이 있으면 한정 이름을 알아야 한다. Codex 이름에는 `@`가 들어갈 수 있어 해석 규칙이 필요하다(마지막 `@` 뒤가 알려진 별칭일 때만 한정자로 본다).

### C. 우선순위 규칙으로 자동 선택

- 방식: 여러 개가 일치하면 같은 cwd(프로젝트), 같은 런타임, 최근 활동 순으로 하나를 고른다
- 장점: 대부분의 호출이 맨 이름으로 끝난다
- 단점: 조용한 오배송 위험이 있다. 규칙을 모르는 사용자나 에이전트에게 예측하기 어렵다

### D. ref 전용

- 방식: 이름은 표시용으로만 쓰고 호출은 항상 ref나 id로 한다
- 장점: 모호성이 없다
- 단점: 사람과 에이전트가 쓰기 어렵다. INTENT.md의 "자연스러운 호출"과 멀다

## 결정 전에 정할 세부

- 홈 별칭을 폴더 이름에서 자동 파생할지(`claude-4`), 사용자가 붙이게 할지(`claude-4` → `work`)
- 맨 이름이 여럿과 일치할 때 항상 오류를 낼지(B), 같은 프로젝트를 우선할지(B+C 혼합)
- Codex의 기본 라벨(첫 메시지 미리보기)도 이름 후보에 넣을지. 넣으면 의도치 않은 일치가 생길 수 있다

## 결정

**B를 택한다**(사용자의 계획 승인 2026-09-20, xsm v0.1로 구현).

- **주소.** `이름`, `이름@홈`, `이름 [ref]`, `ref:xxxxxx`, `claude:<id>`, `codex:<id>`. `@` 뒤는 알려진 홈 별칭일 때만 한정자로 본다. Codex 이름에는 `@`가 들어갈 수 있다.
- **ref.** `sha256("runtime:realpath(home):session_id")`의 앞 6자다. 메시지 헤더는 발신자를 ref로 싣는다.
- **해석.** 살아 있는 일치가 둘 이상이면 후보를 보이고 거부한다. 멈춘 것만 일치하면 재개 명령을 보인다. 열려 있지만 미등록이면 그 이유를 보인다.
- **이름의 출처.** 이름은 런타임이 정한다(Claude 네이티브 기록, Codex 상태 DB). 사람이 고른 이름이 아니면(`derived`, `auto`) `xsm who`가 ref를 쓰라고 알린다. xsm이 띄운 워커는 워커 이름을 쓴다.
